## 第一章 一句话认知：这个系统到底是什么

### 1.1 它解决的真实痛点

"双碳"（碳达峰、碳中和）落地的商业卡点不是"想减碳"，而是**三件事互不信任**：

| 环节 | 现实痛点 | OAISS CHAIN 的解法 |
|---|---|---|
| 算得准吗 | 企业自报排放量，口径随意、数据可改 | 国标 GB/T 32150 参数化模型 + 活动数据×排放因子强制计算 + **RSA/SM2 数字签名**固化 |
| 谁来背书 | 审核员盖章，但报告本身可能是 PS 的 | 审核流转状态机 + **Fabric 联盟链存证**（哈希上链，事后改不动） |
| 怎么交易履约 | 配额富余/缺口靠线下撮合，价格不透明 | **双向连续竞价拍卖（CDA）** + P2P 定向转让 + 碳币结算闭环 |

所以这**不是**一个"CRUD 管理系统"，而是一套**带金融属性的多方可信基础设施**。判断它做得好不好，标准是"数据能不能被事后篡改、交易会不会超卖、审核有没有留痕"，而不是"页面好不好看"。

### 1.2 三层可信结构（这是最该讲给听众的一句话）

```
第一层：算得对   → GB/T 32150 发电企业(25参数) / 电网企业(9参数) 国标模型
第二层：改不了   → 数字签名(私钥签名/公钥验签) + 区块链哈希存证
第三层：赖不掉   → 审核状态机 + 审计日志(AOP @AuditLog) + 信用分奖惩
```

## 第二章 架构全景：代码怎么组织

### 2.1 五工程单体 + 微服务混合

```
OAISS CHAIN/
├── oaiss-chain-backend/    Java 17 + Spring Boot 3.2.12   ← 主业务（23 Controller）
├── oaiss-chain-frontend/   Vue 3.5 + TS + Vite + Element Plus ← SPA 单页应用
├── oaiss-chain-ml-service/ Python 3.11 + FastAPI          ← AI 预测（独立进程）
├── oaiss-chain-chaincode/  Go + Fabric contract-api       ← 智能合约
├── deploy/                 compose / k8s / monitoring / nginx / fabric
└── scripts/                api测试 / browser-qa / lifecycle / ops / gates
```

**架构选型意图**：主业务坚持**单体**（模块化包结构）而非微服务，因为碳核算 → 审核 → 交易 → 结算是一条强事务链，拆成分布式事务会牺牲一致性。只有 **AI 预测**被单独拆出，理由是 Python 生态（Prophet/XGBoost/scikit-learn）无法在 JVM 内复用 —— 这是**按技术异构性切分，而不是按组织架构切分**，是正确判断。

### 2.2 六边形架构（端口-适配器）的真实落地

这是本项目最值得讲的设计。区块链这一段做了**标准 Port/Adapter**：

```java
// 端口（业务只依赖抽象）
public interface BlockchainServicePort { ... }

// 适配器 1：真实 Fabric（仅 fabric profile 激活）
@Profile("fabric")
public class FabricBlockchainService implements BlockchainServicePort { ... }

// 适配器 2：Mock 引擎（默认激活）
@Profile("!fabric")
public class MockBlockchainService implements BlockchainServicePort { ... }
```

**设计初衷**：让"新人 5 分钟跑起来"和"生产接真链"不打架。开发时用 Mock 毫秒级返回合法哈希，CI 不需要拖起 4 个 Fabric 容器；生产切 `--spring.profiles.active=fabric` 即换真链，**业务层零改动**。

> ✅ **实测发现本项目的真实状态比 README 更硬**：README 说"默认 Mock"，但当前实例 **Fabric 网络是真实运行并连通��**——
> `/blockchain/status` 返回 `{"connected":true,"mode":"FABRIC","mspId":"Org1MSP","channel":"mychannel","chaincode":"carbon-chaincode","peers":1,"orderers":1}`，
> 且能查到真实区块 `blockNumber:29`、真实交易 `txHash:11aad598...`。
> `docker ps` 中 `peer0.org1.example.com`、`orderer.example.com`、`ca.org1.example.com`、链码容器全部在跑。
> **讲解时应该说"它真的连了链"，而不是"它有个 Mock"。**

### 2.3 请求生命周期（排障主轴）

```
Vue 组件
  → api/*.ts (Axios 封装)
    → request.ts 拦截器：注入 JWT + 分页参数转换(pageNum→page) + 统一错误提示 + 401 自动刷新 Token
      → Vite 代理 /api → localhost:8080
        → JwtAuthenticationFilter（解析 Token → JwtUserDetails）
          → SecurityConfig（@PreAuthorize 角色拦截）
            → @RestController
              → @Service（叠 AOP：审计/限流/权限/数据隔离/分布式锁）
                → Repository (JPA) → MySQL 8
  ← ApiResponse{ code, message, data, meta }   ← 统一响应信封
```

**记住这个链条，80% 的问题都能定位**：页面不显示数据 → 先看 Network 里接口返回 code；接口 401 → 看 Token；接口 403 → 看角色；数据为空但接口 200 → 看数据隔离/软删除条件。

### 2.4 横切关注点：五个自定义 AOP 注解

这是工程规范性的直接体现。`aop/` 目录下有 5 个切面，全部真实实现（非空壳）：

| 注解 | 切面实现 | 作用 | 讲解价值 |
|---|---|---|---|
| `@AuditLog` | AuditLogAspect | 写操作留痕到 OperationLog | 合规审计刚需 |
| `@RateLimit` | RateLimitAspect | 按 IP/用户 限流 | 防刷 |
| `@RequirePermission` | PermissionAspect | 细粒度权限（比角色更细） | RBAC 补强 |
| `@DataIsolation` | DataIsolationAspect | **强制企业只能看自己数据** | 多租户安全关键 |
| `@DistributedLock` | DistributedLockAspect | Redis 分布式锁 + SpEL 动态 key | **防超卖的关键** |

`@DistributedLock` 在撮合引擎上的用法是全场最亮的工程细节之一：

```java
@DistributedLock(key = "'auction:matching'", expireTime = 30, waitTime = 0)
public List<MatchingResultResponse> executeMatching() { ... }
```

**为什么必须锁**：双向拍卖撮合要一次性改"买方余额 + 卖方配额 + 撮合记录 + 交易记录 + 双方企业配额"五处状态。两个请求并发进来会**双花/超卖**。因为是全局出清，所以锁的是**常量 key**（整场串行），而不是每笔订单各自加锁——这是对的取舍：牺牲吞吐换正确性。

## 第三章 四角色业务闭环（角色关联的核心）

### 3.1 主链路：一份碳报告的一生

这是理解整个系统的**唯一主线**。把这条线讲透，所有页面就都串起来了。

```
①企业填报 ──→ ②数字签名 ──→ ③提交审核 ──→ ④审核员审核通过 ──→ ⑤系统自动上链 ──→ ⑥信用加分
   (上传审核页)   (自动RSA/SM2)   (状态:待审核)   (通过/驳回)    (Fabric存证)      (信誉评分+5)
                                                    │                │
                                                    ↓驳              ↓
                                              信用扣10分        报告哈希进区块
                                              (信誉评分页)      (区块链浏览器)
```

实测状态机（`ReportStatusEnum`）：`草稿 → 待审核 → 审核通过 → 已上链`，任一环节可 `审核拒绝`。

**关键设计点（容易被忽略但很重要）**：
- **签名先于提交**。报告创建时就自动签名（`signatureValid`），审核员在审核页能看到"验签"列——如果报告数据在提交后被改过，验签就失败。这是"防篡改"从口号变成机制的落点。
- **审核即上链（方案 A，2026-10-21 定稿）**。审核员（REVIEWER）审核通过后，**系统后台自动上链**，不再设第二道人工核准。
  > 依据：`docs/raw` 原始需求「当数据审核员点击提交碳排放报告后，系统后台自动将该报告进行上链」。
  > 监管（THIRD_PARTY）**不参与上链审批**，仅作穿透式只读核查（依据 L1「定期核查」+ L2 §3.1/§4.14）。
  > 制衡机制为「企业签名防抵赖 + 审核员合规判断 + 链上存证不可篡改」三层，而非角色双签。
- **加分/扣分自动触发**。通过 +5、驳回 −10，由 `applyApprovedReportSideEffects()` 自动执行，无需人工。这把"信用分"从装饰变成了**有经济后果的约束**（低于阈值会禁交易/冻账户）。

### 3.2 交易闭环

```
企业配额(quota) ─┬─→ 双向拍卖(CDA)：匿名撮合，价优者得，成交价=(买价+卖价)/2
                └─→ P2P 定向：指定对手方，双边协商
                        ↓
                  碳币结算(DVP 钱货两讫)：扣买方冻结资金 + 划卖方配额
                        ↓
                  交易记录 → Fabric 存证 → 信用加分
```

**CDA 撮合的核心规则（务必讲准）**：
1. 价格优先、时间优先排序买卖队列；
2. 双指针扫描，**买价 ≥ 卖价**即成交（存在价格重叠空间）；
3. 成交价取**中间价** `(P_buy + P_sell)/2`；
4. 买方按挂单价冻结资金，成交价更低时**自动退回差价**（`priceDiff × matchQty`）——这是保护买方的重要细节，很多同类系统会漏；
5. 全过程 `@DistributedLock` 串行，防超卖。

### 3.3 四角色权责矩阵（实测确认）

| | 企业 ENTERPRISE | 审核员 REVIEWER | 监管 THIRD_PARTY | 管理员 ADMIN |
|---|---|---|---|---|
| **首页** | /enterprise/carbon/upload | /auditor/audit/list | /third-party/monitor | /admin/system/users |
| **菜单数** | 11 项（含 4 个分组） | 2 项 | 1 项 | 5 项 |
| **能做什么** | 填报/算碳/**发起交易**/看碳币/看信用/申请碳中和项目/用 AI | 审核报告/核证项目/查历史 | 宏观监控/验收核准/机构信息 | 用户赋权/证书签发/系统配置/全局统计 |
| **不能做什么** | ❌不能自审 ❌不能签发证书 | ❌不能改企业数据 ❌不能自己上链 | ❌不能代企业填数据 | ❌不参与具体交易 |
| **本质定位** | 数据生产方 + 交易方 | 合规裁判 | 最终背书方 | 平台运维方 |

**角色关联的精髓**：四个角色不是并列的四个后台，而是一条**制衡链**。任何一方都无法单独完成"改数据→变合法"的闭环：
- 企业能改自己的数据 → 但一改签名就废；
- 审核员审核通过 → 系统自动上链（无第二道人工核准，监管不参与上链审批）；
- 监管能核准 → 但数据是企业和审核员给的，改不了原始值；
- 管理员权限最大 → 但所有操作进审计日志（`@AuditLog`）。

### 3.4 登录与鉴权机制（实测）

- 登录需 **账号 + 密码 + 图形验证码**三要素；
- 验证码为 6 位随机码，存入 Redis（`captcha:<key>`，5 分钟 TTL），带**失败降级到本地内存**的兜底；
- 成功后返回 JWT（`accessToken` + `refreshToken`），前端存 `localStorage`/（记住我）`sessionStorage`；
- Token 内含 `roles` 与 `userType`（1 企业/2 审核员/3 监管/4 管理员），前端据此算 `homePath` 和菜单；
- 过期自动刷新（`request.ts` 拦截 401 → 用 refreshToken 换新 → 重放原请求）。

> **演示提示**：密码统一 `admin123`，账号 `enterprise001` / `reviewer001` / `thirdparty001` / `admin`。验证码是图片，需要现场看屏幕输入——如果做录屏演示，建议先登录好四个浏览器标签页。

- **讲解要点**：这是**第一印象页**，做得相当完整。亮点是它把"技术可信度"用可视化的方式摆出来（数据指纹、区块高度、加密体系）。⚠️ 但"3248 节点数量 / 11ms 延迟"这类指标是**静态写死的营销数字**，与真实 Fabric（1 peer / 1 orderer）不一致，正式汇报时**不要当成实测性能**讲。

#### ② 登录页 `/login`
- **表单**：账号 / 密码 / 验证码（三字段，均必填）。
- **怎么操作**：输入任一预置账号 → 密码 `admin123` → 看右侧验证码图片输入 4–6 位字符 → 点"登录"。验证码可点击刷新。
- **讲解要点**：验证码是**服务端生成、Redis 存储、5 分钟过期**的真实实现，不是前端假图。这是防暴力破解的第一道闸。

### 4.2 企业端（15 个页面，系统最核心的体验区）

> 进入后统一布局：左侧深绿侧边栏（碳核算 / P2P订单管理 / 碳交易▾ / 本公司信息▾ / 信誉评分 / 碳币账户 / 区块链 / 碳中和▾ / AI智能预测▾ / 个人中心），顶部面包屑 + "监管模式"角标 + 通知铃铛（实测 7 条未读）+ 用户名 + 中英文切换 + 退出。
> **首次进入会弹「3 步上手」引导弹窗**（第1步·填一份碳排放报告 → 第2步/第3步 → 提供"去创建第一份报告"快捷按钮）。这是**很好的新手引导设计**，但注意它会在**每一个**子页面重复弹出（实测跳转新页面必弹），这是明显体验缺陷，详见第六章。

#### ③ 碳核算（上传审核）`/enterprise/carbon/upload` ⭐核心入口
- **这是什么**：企业碳报告的全生命周期工作台，也是企业登录后的**默认首页**。
- **上面有什么**：顶部引导条"把今年烧的煤、用的电填进来"→ 创建区（报告标题 + 核算周期 + 【创建】）→ 报告表格：报告编号 / 报告标题 / 核算周期 / 总排放量(tCO2e)ⓘ / 状态 / 签名ⓘ / 审核人 / 创建时间 / 操作（查看详情·提交·删除）。
- **怎么操作**：
  1. 填报告标题 + 选核算周期（如 2026-Q1）→ 点【创建】；
  2. 进详情页填**活动数据 × 排放因子**（按 Scope1 直接燃烧 / Scope2 外购电 / Scope3 其他 分组）；
  3. 系统自动算总量 + **自动生成数字签名**（列表"签名"列显示"已签名"）；
  4. 点【提交】→ 状态变"待审核"；
  5. 审核结果回写：通过→"审核通过"，驳回→"审核拒绝"。
- **讲解要点**：**这是全系统的起点**。三个必讲细节：① 总排放量是**算出来的**不是填的（活动数据×因子）；② 创建即签名，签名是后续防篡改的锚；③ 状态列就是那台"报告状态机"的可视化。

#### ④ P2P 订单管理 `/enterprise/orders/manage`
- **上面有什么**：筛选区（交易编号 / 交易类型 / 日期范围）+ 表格：序号 / 交易编号 / 交易类型 / 交易对手 / 数量 / 单价 / 总金额 / 交易状态 / 创建时间 / 操作。
- **怎么操作**：按编号/类型/日期筛选 → 点【查询】/【重置】→ 逐行【查看详情】看交易明细。
- **讲解要点**：这是**交易台账**，只读为主。能一眼看出"我的配额卖给了谁、卖了多少钱"。交易类型区分 CDA 拍卖成交 与 P2P 定向转让。

#### ⑤ 双向拍卖 `/enterprise/trading/market` ⭐技术亮点页
- **上面有什么**：页签【全部挂单 / 我的挂单 / 撮合结果】+【查询】【创建订单】+ 表格：序号 / 买卖方向 / 数量（吨）/ 价格（元/吨）/ 状态 / 创建时间。实测已有 10+ 条挂单（买/卖混合，价格 25–45 元/吨，状态"待撮合"/"已成交"）。
- **怎么操作**：点【创建订单】→ 选买卖方向 + 填数量 + 填价格 → 提交（买方冻结资金/卖方冻结配额）→ 切"撮合结果"页签看成交。
- **讲解要点**：**这是最该重点讲的技术页**。讲清三件事：① 匿名竞价——看不到对手是谁，只看价格；② 价格优先+时间优先，买价≥卖价即成交；③ 成交价取中间价、买方差价退回、全程分布式锁防超卖。
- **⚠️ 已知缺陷**：本页会触发一个 401 失败请求（`POST /copilot/procurement-advice`），即"AI 智能采购助手"功能后端未接通。演示时**不要点这个按钮**，或提前说明"AI 助手依赖 ML 服务密钥配置，当前环境未开启"。

#### ⑥ P2P 交易 `/enterprise/trading/p2p`
- **上面有什么**：【创建P2P交易】+ 筛选（交易对手 / 身份 / 交易编号）+ 表格：序号 / 交易编号 / 买方名称 / 卖方名称 / 交易数量 / 单价 / 总金额 / 状态 / 创建时间 / 操作。
- **怎么操作**：点【创建P2P交易】→ 填**交易对手企业ID** + 交易数量 + 单价 → 弹确认框【确认】/【取消】。
- **讲解要点**：与拍卖的区别——P2P 是**双边协商、点对点、指定对手方**，适合长期合作方；拍卖是**匿名、多方、价优者得**。两者共用底层结算（碳币 + 配额划转）。

#### ⑦ 数据可视化 `/enterprise/company/dashboard`
- **上面有什么**：日/月/年 三个时间维度切换 + 图表区。
- **讲解要点**：企业侧的经营驾驶舱。⚠️ **实测内容偏单薄**（页面文字仅 475 字符，图表数据依赖报告数据量），是明显的"待充实"页面。

#### ⑧ 信誉评分 `/enterprise/credit/score` ⭐
- **上面有什么**：当前评分大数字（实测 90 分，等级"优秀"）+ 更新时间 + 两块表格：①「评分历史」序号/事件类型/变化值/原因/时间；②「评分排名」序号/企业名称/评分/等级/交易权限。
- **怎么操作**：只读页。看评分构成、看自己在全平台的名次、看有无交易权限限制。
- **讲解要点**：**信用分不是摆设**，它直接决定"能不能交易"（`tradeRestricted`）和"账户是否冻结"（`accountFrozen`）。奖惩规则：审核通过 +5；驳回 −10；实测历史里有"轻微违规 −10"和连续多条"良好行为奖励 +5"。
- **⚠️ 明显缺陷**：事件"原因"列显示的是**英文原始串**（`Carbon report certification reward`、`Carbon report audit rejected: report_xxx`），因为后端直接把这些英文写进了数据库，前端不做翻译。中文界面里冒出英文，是很扎眼的本地化漏洞。

#### ⑨ 碳币账户 `/enterprise/carbon-coin/account`
- **上面有什么**：「账户信息」卡片（可用余额 / 冻结余额 / 累计充值 / 累计消费）+【转账】按钮；「交易记录」表格：序号 / 交易编号 / 交易类型 / 金额 / 交易后余额 / 备注 / 时间。
- **怎么操作**：点【转账】→ 填收款方 + 金额 → 确认。交易类型区分 充值/消费/冻结/解冻/退款。
- **讲解要点**：实测余额 3902.98、冻结 1055、累计充值 15510.1、累计消费 11693.12 —— 这组数字正好体现**"挂单冻结"机制**：挂买单会冻结资金，成交才真正扣除，撤单/差价退回则解冻。这是交易所级资金模型。

#### ⑩ 区块链浏览器 `/enterprise/blockchain/browser` ⭐技术亮点页
- **上面有什么**：页签【最新区块 / 交易记录】+【查询交易】+ 区块表：操作 / 区块高度ⓘ / 区块哈希 / 区块类型 / 交易数量 / 矿工地址 / 时间戳；交易表：操作 / 交易哈希ⓘ / 区块高度 / 发送方 / 接收方 / 金额 / 状态 / 时间戳。
- **怎么操作**：浏览区块列表 → 点【查询交易】按哈希精确检索 → 逐层下钻到交易详情。
- **讲解要点**：**这是"可信"的物证页**。实测能查到真实区块（高度 29、哈希 `0xf93caa0b...`、3 笔交易）和真实交易（`11aad598...`、状态 VALID）。要强调：这里显示的不是数据库表，而是**从 Fabric Peer 实时查回来的链上数据**（`/blockchain/status` 实测返回 `mode:FABRIC, connected:true`）。

#### ⑪ 碳中和项目 `/enterprise/carbon-neutral/projects`
- **上面有什么**：【创建项目】+ 表格：序号 / 项目名称 / 项目类型 / 项目描述 / 预期减排量(吨)(tCO₂e) / 状态 / 开始日期 / 结束日期 / 创建时间 / 操作（详情）。
- **怎么操作**：创建项目（名称/类型/预期减排量/周期）→ 提交审核 → 审核通过后启动 → 提交核证 → 申请认证 → 认证完成获得碳信用（Credits）→ 可用于抵消。
- **讲解要点**：这是 CCER（国家核证自愿减排量）的业务模拟。项目生命周期比碳报告更复杂：`筹备中→待审核→审核通过/拒绝→进行中→已核证→已认证→已完成/已终止`。实测平台已有 64 个项目，状态分布：已完成 15 / 审核拒绝 15 / 已终止 15 / 筹备中 15 / 待审核 3 / 审核通过 1。
- **⚠️ 已知缺陷**：审核员侧的"项目核证"页显示**暂无数据**，但后端确有 64 个项目且 15 个"已核证"。这是**数据隔离与筛选条件不匹配**导致的可见性断裂，详见第六章。

#### ⑫ 排放数据 `/enterprise/emission/data`
- **上面有什么**：页签【排放评级 / 行业排名 / AI预测】+表单（企业ID / 预测月数）+【AI预测】按钮 + 两张表：评级（操作/评级ⓘ/总排放量/行业均值/评分/评级时间）、排名（排名/企业名称/总排放量/评级ⓘ/评分）。
- **怎么操作**：切"排放评级"看自己的 A/B/C 评级与评分；切"行业排名"看同业位次；切"AI预测"填月数→点【AI预测】出走势。
- **讲解要点**：把"算得多准"变成"横向可比"——评级 + 百分位（percentile）让企业知道自己在行业里什么水平。实测企业评级 A、评分 100。
- **⚠️ 已知缺陷**：`POST /emission/predict` 实测返回 **HTTP 500**（详见第六章根因分析）。演示 AI 预测请改用「AI市场预测」页，那条链路是通的。

#### ⑬ 个人中心 `/enterprise/user/profile`
- **上面有什么**：页签【基本信息 / 修改密码】；「我的准入证书」卡片；「数字签名」卡片（管理企业 RSA 密钥对，含【刷新状态】【删除密钥对】）；表单：用户名 / 角色 / 真实姓名 / 邮箱 / 手机号 / 公司 / 地址 / 在线停留时长 / 当前密码 / 新密码 / 确认密码。
- **怎么操作**：改联系方式→【保存修改】；改密码→填三个密码字段→【修改密码】；密钥对可刷新/吊销。
- **讲解要点**：**密钥对管理是企业侧最安全敏感的操作**。删了密钥对就签不了名，报告发不出去——这是"数字身份"的现实体现。建议演示时**不要真删**。

#### ⑭ AI 市场预测 `/enterprise/market-prediction` ⭐技术亮点页
- **上面有什么**：顶部四指标卡（现货基准价 58.20 元/吨、置信区间、预测算法架构 Prophet + XGBoost、引擎驱动版本 1.0.0）+ 时间粒度切换（7天/30天/90天/180天）+ 碳市场预测走势图 + 「AI 碳价敏感度与多情景动态推演沙盘」（三个滑杆：动力煤现货价格变动率 ±20%、国家配额基准线紧缩幅度 ±10%、区域绿电消纳替代率增量 +30%）+ 情景推演结果（预测价格/基准偏差）+ 「XAI 多因素特征归因分析 SHAP 贡献权重」+ 「AI 量化操盘与企业履约决策建议」+【前往双向拍卖挂单】。
- **怎么操作**：选时间粒度 → 拖动三个滑杆 → 实时看右侧预测价与偏差 → 读下方归因与建议 → 点【前往双向拍卖挂单】直接跳去下单（**很好的业务闭环设计**）。
- **讲解要点**：这是**全项目最"产品化"的页面**。三个必讲：① 双模型融合（Prophet 做时序趋势、XGBoost 做特征回归）；② **XAI 可解释性**（SHAP 告诉你"价格为什么变"，而不是黑盒给个数）；③ 情景沙盘把"如果我成本涨 10% 会怎样"变成可交互推演——这对企业做**履约决策**（现在买还是等等）有真实价值。实测后端 `/ai/market/trend|price|supply-demand` 全部 200 正常。

#### ⑮ AI 企业推理 `/enterprise/enterprise-inference` ⭐技术亮点页
- **上面有什么**：「多维碳排放与合规特征偏离诊断 · 国标基准线比对」——六个维度条：范围一燃烧受控度(88)、范围二绿电清洁度(78)、信用履约历史(85)、报告周期规律性(92)、碳配额流动储备(84)、脱硫工艺受控度(80)；「风险因素深度穿透解析 · 3 项待关注」；「AI 智能企业降碳与能效跃升实施路径」+【前往公式测算】【采购配额履约】【生成企业低碳体检白皮书】。
- **怎么操作**：点【刷新】重算 → 读六维雷达 → 看风险清单 → 沿"实施路径"跳去公式测算或去采购配额。
- **讲解要点**：这是把 **IsolationForest 异常检测**产品化的结果。实测后端返回：`complianceStatus: compliant`、`confidence: 0.9976`、`anomalyScore: -0.189`、`isAnomaly: true`，风险因素含"High compliance flag count"、"Anomalous emission pattern detected"。讲解重点：**它不只是告诉你"你不合规"，而是给出六个可解释维度 + 具体行动路径**。

#### ⑯ 碳核算公式 `/enterprise/carbon-formula` ⭐国标落地页
- **上面有什么**：页签【发电行业 / 电网行业】+ 年份/企业名 → 发电行业按燃料分组折叠面板（原煤 / 洗精煤 / 其他洗煤 / 型煤 / 其他煤制品 …），每组四个参数：**燃料消耗量(FC) / 低位发热量(NCV) / 含碳量(CC) / 碳氧化率(OF)**，各带【实测反推】按钮；下方「脱硫过程排放」：碳酸盐消耗量 / 脱硫排放因子 / 脱硫转化率；【载入火电机组典型样本】【计算】。电网行业：输送电量 / 线损率 / 电网排放因子 / 发电量 / 购入电量 / 输出电量 / 购入电力排放因子 + 【载入电网输配电典型样本】【计算】。右上角【国标法规智囊 Copilot】。
- **怎么操作**：选页签 → 点【载入典型样本】一键填充国标默认值 → 手工改某个参数 → 点【计算】→ 看结果。不熟悉参数时点【实测反推】从已知结果倒推参数。
- **讲解要点**：**这是全项目的技术底座**。必须讲清核心公式：
  ```
  排放量 = 燃料消耗量(FC) × 低位发热量(NCV) × 单位热值含碳量(CC) × 碳氧化率(OF) × 44/12
  ```
  （44/12 是碳→二氧化碳的分子量换算）。发电企业 25 项参数、电网企业 9 项参数，**完全对齐 GB/T 32150 国标**。【实测反推】按钮体现了工程上的体贴：现场往往测不到 CC，但能测到总排放，就能反算。
- **⚠️ 已知缺陷**：右上【国标法规智囊 Copilot】抽屉会调 `/copilot/policy-qa`，实测 401 失败（同第⑤页根因）。

#### ⑰ 企业信息 `/enterprise/info`
- **上面有什么**：「企业基本信息」卡片 +【编辑联系方式】；「碳配额信息」卡片（总配额/已用/剩余/可交易/使用率）。
- **怎么操作**：点【编辑联系方式】改联系人信息。
- **讲解要点**：实测配额数据：总配额 50025 吨、已用 12090 吨、剩余 37935 吨、可交易 37944 吨、使用率 24.17%。**注意"剩余"与"可交易"不等**——差额是被挂单冻结的部分，这个细节能体现系统资金/配额模型的严谨性。

### 4.3 审核员端（3 个页面）

## 第五章 开发亮点与设计初衷

> 这一章是"能被追问"的部分。每条都给出**证据位置**，避免空谈。

### 5.1 十个真正值得讲的亮点

**① 国标算法参数化，而非硬编码**
GB/T 32150 的 25 项（发电）/ 9 项（电网）参数被抽象成独立的 `PowerGenerationFormulaService` / `PowerGridFormulaService`，燃料类型按分组配置。**设计初衷**：国标会修订，参数会变，参数化后改配置不改代码。
证据：`service/PowerGenerationFormulaService.java`（9.8KB）、`PowerGridFormulaService.java`（4.8KB）。

**② 签名与加密是双轨自适应（RSA + 国密 SM2）**
这一条 **README 没写全**。实际实现是 `SignatureStrategy` 策略模式 + 工厂，同时支持 `RsaSignatureStrategy` 和 `Sm2SignatureStrategy`，运行时按公钥特征自动解析用哪套算法。
**设计初衷**：国内政企项目必须过商用密码合规（国密 SM2/SM3），但国际互操作要 RSA。双轨并存是**唯一能同时满足两者的方案**。
证据：`security/crypto/{SignatureStrategy,SignatureStrategyFactory,RsaSignatureStrategy,Sm2SignatureStrategy}.java`；`DigitalSignatureService.resolveStrategy()`。

**③ 事务性发件箱（Transactional Outbox）保证"数据库与链上最终一致"**
这是全场**最硬核**的分布式设计。存证不是直接调链，而是：业务事务里写一条 `OutboxMessage(PENDING)` → 异步扫描器提交链 → 成功置 SENT / 失败按退避重试 / 超次数进 DEAD 死信。
**设计初衷**：链上调用可能超时或失败。如果先上链后写库，链成功库失败就丢数据；如果先写库后上链，上链失败就账链不一致。Outbox 用"本地事务 + 至少一次投递"解决这个经典难题。
证据：`service/OutboxService.java`（状态机 PENDING/SENT/FAILED/DEAD + `@DistributedLock("'outbox:retry:scanner'")`）、`event/BlockchainEventListener.java`。

**④ 区块链走 Port/Adapter + Spring Profile 双实现**
`BlockchainServicePort` 接口 + `@Profile("fabric")` / `@Profile("!fabric")` 两个适配器。业务层零感知。
**设计初衷**：开发不需要拖 Fabric 网络（4 个容器 + 证书），生产一键切真链。
**实测彩蛋**：当前实例其实**真的连了 Fabric**（`mode:FABRIC, connected:true`，区块 29、交易 32 笔），比文档宣称的"默认 Mock"更硬。

**⑤ 撮合引擎的"差价退回"细节**
买方按挂单价冻结资金，成交价是中间价。若成交价低于挂单价，系统自动 `refund = (buyPrice - settlePrice) × matchQty` 退回。
**设计初衷**：不这么做，买方就吃亏了——他会一直按最高价冻结资金。这个细节是"交易所级"的体现，很多毕设/外包项目会漏。
证据：`DoubleAuctionService.executeMatching()` 第 275–279 行。

**⑥ 全局撮合锁 + 局部读写分离的取舍**
`@DistributedLock(key="'auction:matching'", expireTime=30, waitTime=0)`——用**常量 key 整场串行**，而不是每笔订单加锁。
**设计初衷**：CDA 出清是"全局匹配"，两笔互不相干的订单也可能影响同一个价格队列。牺牲吞吐换正确性，是正确的工程判断。`waitTime=0` 也是刻意的——拿不到锁立即失败，避免请求堆积。

**⑦ 五个 AOP 注解把合规做成"声明式"**
审计、限流、权限、数据隔离、分布式锁全部注解化。业务代码里几乎看不到 `if` 判断权限。
**设计初衷**：合规是横切关注点，散落在业务里必然漏。注解化后**新增接口自动获得审计**，这才是可维护的合规。
证据：`aop/*Aspect.java` 五个文件 + `annotation/*.java`。

**⑧ 熔断降级，AI 不可用不影响主业务**
`MlServiceClient` 用 Resilience4j `CircuitBreaker` 包所有 ML 调用，失败/超时走 `fallbackMarketForecast()` 返回兜底数据，并打点 `ml.service.degraded` 指标。
**设计初衷**：AI 是增强功能，不能因为 Python 服务挂了就让企业下不了单。
证据：`service/ml/MlServiceClient.java`（每个方法都有 `onErrorResume` 双兜底）。

**⑨ 软删除 + 数据隔离的组合拳**
所有实体继承 `BaseEntity`（`deleted` 字段），查询一律 `...AndDeletedFalse`；再叠 `@DataIsolation` 保证企业只能看自己的数据。
**设计初衷**：碳数据有法定留存要求，**物理删除是违规的**。软删除既满足"用户以为删了"，又满足"监管要能查"。

**⑩ 带自动刷新的 JWT 会话**
`request.ts` 拦截器发现 401 → 用 refreshToken 换新 → **重放原请求**，且用 `pendingRequests` 队列避免并发刷新风暴。
**设计初衷**：Token 1 小时过期，用户正填表时过期会丢数据。自动续期 + 请求重放是体验刚需。

### 5.2 一句话讲清"设计初衷"（对外介绍用）

> "这个系统的设计出发点，是**把'我减了多少碳'从一句自说自话，变成一条任何人都改不了、赖不掉的证据链**。
> 算得准靠国标算法，改不了靠数字签名，赖不掉靠联盟链存证，用得上靠交易撮合和 AI 决策。
> 技术上最难的不是这些单点，而是让它们**在一条事务链上不打架**——所以我们用了 Outbox 保证账链一致、用分布式锁保证不超卖、用端口适配器让开发环境和生产环境解耦。"

## 第六章 现存不足与优化建议

> 全部为**实测复现**的问题，附证据与修复建议。按严重度排序。

### P0 · 阻断级（功能不可用，演示会翻车）

#### 缺陷 1：AI Copilot 三个端点全部 401，前端功能形同虚设
- **现象**：企业端「双向拍卖」页加载时抛出 `401 POST /copilot/procurement-advice`；「碳核算公式」的【国标法规智囊 Copilot】和报告分析同样失败。
- **根因链（已完整定位）**：
  1. 前端 `api/auction.ts:101` 直接 `fetch('/copilot/procurement-advice')`，经 Vite 代理 `/copilot → localhost:8001` 打到 **ML 服务**；
  2. ML 服务 `app/routers/copilot_router.py` 三个端点都挂了 `Depends(require_ml_service_secret)`，要求 `X-ML-Service-Secret` 头；
  3. 但前端**从不带这个头**（浏览器也不该持有服务端密钥）；
  4. 且 `.env` 中 `ML_SERVICE_SECRET` **为空**，后端 `MlServiceConfig:60` 的 `if (!secret.isBlank())` 判定为 false，后端**也不发这个头**；
  5. 结果：ML 服务用默认密钥 `oaiss-ml-shared-secret-key-2026` 校验，收到空头 → 401。
- **实测佐证**：直接带默认密钥请求 ML，三个端点全部 200 且返回高质量中文结果（如采购建议："企业目前存在 200.00 吨的配额缺口，预估平仓成本约 11,640.00 元…"）。**说明模型是好的，只是链路没接上。**
- **修复建议（三选一，推荐 A）**：
  - **A（正解）**：前端改为调后端 `/api/v1/copilot/*`，新增一个 Spring `CopilotController` 走 `MlServiceClient` 代理转发。优势：密钥只在后端、可复用熔断降级、可加权限与审计。
  - B：Vite 代理加 `headers: {'X-ML-Service-Secret': ...}`（仅能救开发环境，生产 Nginx 还要再配一遍，且把密钥暴露给构建产物）。
  - C：ML 侧对 copilot 放开鉴权（**不推荐**，等于拆掉服务端防护）。
  - 配套：`.env` / `.env.example` 里把 `ML_SERVICE_SECRET` 从空值改为必填并加校验启动失败。

#### 缺陷 2：`POST /emission/predict` 返回 HTTP 500
- **现象**：「排放数据」页 → AI预测 页签 → 点【AI预测】→ 500。
- **根因**：`CarbonPredictionService.predict()` 第 80 行调 `mlServiceClient.predictEmission()`；ML 调用因密钥缺失失败后走 fallback 返回了对象，但后续 `mapToResponse()` 中 `mlResponse.getForecastDates()` 相关字段为 null 或类型不匹配抛 NPE（ML 直连测试同一请求是 200，证明 ML 侧正常）。同时 `/emission/predict` 是**唯一没有走 `onErrorResume` 兜底**的 ML 调用（`predictEmission` 分支），暴露了降级策略覆盖不全。
- **修复建议**：① 统一 `MlServiceClient` 全部方法都加 `onErrorResume` 兜底；② `mapToResponse` 对 null 做防御；③ 补一条集成测试覆盖"ML 不可用时预测接口应返回 `confidence:0.1 + message` 而不是 500"。

### P1 · 高（业务数据看起来"坏了"，影响可信度）

#### 缺陷 3：审核员「项目核证」页永远空白，与已有数据矛盾
- **现象**：`/auditor/project/review` 显示"暂无数据 / 共 0 条"；但平台实有 **64 个碳中和项目**，其中 15 个"已核证"。
- **根因**：`GET /carbon-neutral/pending-verification` 实测 `totalElements: 0`。该方法按 `verifierId = 当前登录审核员` 过滤，但历史数据里的 `verifierId` 并非 `reviewer001(userId=1)`，而是测试数据里其他人（如"张三"）。**数据初始化未把待核证项目分配给现有审核员**。
- **修复建议**：① 种子数据生成时把 pending 项目 `verifierId` 赋给 `reviewer001`；② 或改为"未核证项目池 + 认领"模式（更符合真实业务，避免审核员只看到分给自己的）。

#### 缺陷 4：信用事件"原因"列显示英文原始串
- **现象**：「信誉评分」页评分历史里显示 `Carbon report certification reward`、`Carbon report audit rejected: report_17924...`。
- **根因**：后端把英文写死进数据库——`CarbonService.java:183` `"Carbon report audit rejected: " + reportNo`、`:392` `"Carbon report certification reward"`。前端只做展示不做翻译。
- **修复建议**：改为**存事件类型枚举 + 参数**（如 `eventType=CERT_REWARD, params={reportNo}`），前端按 i18n key 渲染。这样中英文都能正确显示，也便于统计归因。

#### 缺陷 5：指引弹窗「3 步上手」在每个页面重复弹出

- **根因**：引导状态未持久化（未写 localStorage / 未记后端），路由切换重新挂载即重弹。

### 7.2 高频提问 Q&A

**Q：区块链是不是硬凑的？把哈希存数据库不也一样？**
A：不一样。哈希存数据库只解决"防篡改"，解决不了"**谁有权改**"。联盟链的价值是**多方共同维护**——企业、审核员、监管各持一份账本，任何一方改都要多数共识。而且本系统用了**事务性 Outbox** 保证"数据库写入"与"链上存证"的最终一致，这是把链真正嵌进业务流程，不是外挂装饰。

**Q：AI 预测准吗？**
A：不要说"准"。要说：**它给的是带置信区间的决策参考，不是精确预言**。技术上 Prophet 抓季节性与趋势、XGBoost 做多因子回归、IsolationForest 做异常检测；产品上通过 SHAP 告诉你"为什么"，通过情景沙盘告诉你"如果…会怎样"。企业拿它做**履约时点决策**（现在买还是等），不是拿来当算命。

**Q：四个角色为什么这么分？**
A：核心是**互相制衡**。企业能造数据但改不了签名；审核员能判合规但碰不了原始数据，**审核通过即自动上链**（方案 A），失败时也只能由审核员做幂等补救；监管只能看、不能改、不参与审批；管理员权限最大但一切进审计日志。**没有任何单点能完成"改数据→变合法"**，这才是这套角色设计的真正目的。

**Q：这个项目最大的技术难点是什么？**
A：不是单点技术，是**一致性**。一条业务链要同时保证：业务库事务、链上存证、资金/配额划转、信用分变更四者不错乱。解法是 Outbox（库链一致）+ Redis 分布式锁（防超卖）+ 端口适配器（环境解耦）+ 熔断降级（AI 故障不拖垮主链路）。
