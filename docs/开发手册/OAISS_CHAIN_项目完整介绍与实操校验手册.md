## 第 1 章 系统是什么：业务问题、技术定位与架构分层

### 1.1 功能概述

OAISS CHAIN 是一套面向「双碳」（碳达峰、碳中和）的**多方可信碳资产管理平台**。它要解决的不是「记录碳排放」，而是三个互不信任的角色之间的**数据可信问题**：

| 现实痛点 | 系统手段 |
|---|---|
| 企业自报排放量，口径随意、可事后修改 | 国标参数化核算模型 + 强制数字签名 |
| 审核员盖章，但无法证明报告未被 PS | 审核流转状态机 + 联盟链哈希存证 |
| 配额余缺靠线下撮合，价格不透明、可能超卖 | 双向连续竞价拍卖 + 分布式锁 + 券款对付结算 |

### 1.2 入口页面 / 路径

| 入口 | 地址 | 说明 |
|---|---|---|
| 官网首页 | `http://localhost:5173/official-home` | 未登录默认落地页 |
| 登录页 | `http://localhost:5173/login` | 四角色统一入口 |
| 角色首页 | 企业 `/enterprise/carbon/upload`；审核员 `/auditor/audit/list`；监管 `/third-party/monitor`；管理员 `/admin/system/users` | 由 `config/menu.ts` 的 `ROLE_HOME` 决定 |
| Swagger | `http://localhost:8080/api/v1/swagger-ui/index.html` | 在线调全部 146 端点 |

### 1.3 涉及角色与权限

四角色：`ENTERPRISE`（企业）/ `REVIEWER`（审核员）/ `THIRD_PARTY`（第三方监管）/ `ADMIN`（管理员）。

权限是**双层**的：前端 `router` 的 `meta.roles` 做页面级拦截，后端 `@PreAuthorize("hasRole(...)")` 做接口级拦截。**前端拦截只是体验，后端才是安全边界**——校验越权必须直接打接口（见 9.4）。

### 1.4 关键数据与依赖

```
前端 Vue 3.5 + TS + Vite + Element Plus + Pinia + ECharts
   │ Axios（request.ts 拦截器：JWT 注入 / 分页转换 / 401 刷新 / 统一错误）
   ▼
后端 Java 17 + Spring Boot 3.2.12
   ├─ Security：JwtAuthenticationFilter → SecurityConfig(@PreAuthorize)
   ├─ AOP：@AuditLog / @RateLimit / @RequirePermission / @DataIsolation / @DistributedLock
   ├─ MySQL 8（Flyway V1–V14，现存 24 张表）
   ├─ Redis 7（验证码 / 会话 / 分布式锁 / 限流计数）
   ├─ MinIO（附件对象存储）
   ├─ ML 服务 Python FastAPI:8001（Prophet / XGBoost / IsolationForest / Copilot）
   └─ Hyperledger Fabric（peer0.org1 + orderer，channel=mychannel，chaincode=carbon-chaincode）
```

**架构选型说明（为什么这样切）**：主业务坚持**单体分模块**而不拆微服务，因为「核算→审核→交易→结算」是一条强事务链，拆开就要做分布式事务，得不偿失。只有 **AI 预测**被单独拆成 Python 进程，因为 Prophet/XGBoost 生态无法在 JVM 内复用——这是**按技术异构性切分，不是按组织架构切分**。

区块链这一段采用**端口-适配器（六边形架构）**：业务只依赖 `BlockchainServicePort` 接口，下面挂两个适配器——`@Profile("fabric")` 的真实 `FabricBlockchainService`，和 `@Profile("!fabric")` 的 `MockBlockchainService`。开发时不必拖起 4 个 Fabric 容器，生产切换 profile 即可，业务代码零改动。

### 1.5 术语解释（架构相关，首次出现）

| 术语 | 简明解释 |
|---|---|
| **联盟链（Consortium Blockchain）** | 由多家机构共同维护的区块链，只有被授权节点才能加入和写入。与公有链（人人可参与）不同，牺牲开放性换取可控性与性能，适合政务/金融。本项目用 Hyperledger Fabric。 |
| **通道（Channel）** | Fabric 里的逻辑隔离分区，不同通道数据互不可见。本项目通道名 `mychannel`。 |
| **链码 / 智能合约（Chaincode）** | 跑在 Fabric 容器里的业务逻辑，负责把报告/交易写进账本并保证不可篡改。本项目链码 `carbon-chaincode`，用 Go 写。 |
| **端口-适配器 / 六边形架构** | 业务核心只定义「接口（端口）」，外部依赖通过「实现（适配器）」接入。换数据库/换链只换适配器，内核不动。 |
| **Profile** | Spring 的「环境开关」，用 `--spring.profiles.active=xxx` 激活，同一份代码在不同环境装配不同实现。 |
| **JWT（JSON Web Token）** | 自包含登录凭证：服务端签发签名过的字符串，客户端每次请求带上，服务端验签即知「你是谁、什么角色」，无需查库。本项目有效期 1 小时，配 refreshToken 续期。 |
| **RBAC（基于角色的访问控制）** | 用「角色」而非「具体人」授权。本项目四角色，接口用 `hasRole('REVIEWER')` 这类表达式限制。 |
| **AOP（面向切面编程）** | 把日志、限流、权限、加锁这类**横切关注点**从业务代码抽出，用注解声明式统一处理，避免每个接口手写一遍。 |
| **软删除（Soft Delete）** | 不真删数据，只把 `is_deleted` 置 1，查询时过滤。碳数据有法定留存要求，物理删除违规，故本项目全实体软删除。 |
| **分布式锁** | 多实例/并发下用 Redis 抢同一 key，保证「同一时刻只有一人能改」。用于防交易超卖。 |
| **熔断降级（Circuit Breaker）** | 下游（如 ML）连续失败时自动「跳闸」不再调用，直接返回兜底数据，避免拖垮主业务。 |
| **事务性发件箱（Transactional Outbox）** | 保证「本地库事务」与「外部系统（如区块链）操作」最终一致的经典模式：先在业务事务里写一条待发消息到 outbox 表，再由后台扫描器投递，失败重试、超限进死信。见 9.1。 |

### 1.6 实操校验步骤

1. 确认端口在监听：`Get-NetTCPConnection -State Listen | Where-Object {$_.LocalPort -in 5173,8080,8001,3306,6379,9004} | Select-Object LocalPort`
2. 确认后端健康：`(Invoke-WebRequest 'http://localhost:8080/api/v1/actuator/health' -UseBasicParsing).Content`
3. 确认 Fabric 容器：`docker ps --format '{{.Names}}' | Select-String 'peer|orderer|ca\.|chaincode'`
4. 浏览器打开 `http://localhost:5173/official-home`。

### 1.7 预期结果

- 步骤 1：输出 5173、8080、8001、3306、6379、9004。
- 步骤 2：返回 `{"status":"UP","groups":["liveness","readiness"]}`。
- 步骤 3：至少列出 `peer0.org1.example.com`、`orderer.example.com`、`ca.org1.example.com` 与一个 `dev-peer0...carbon-chaincode`。
- 步骤 4：看到深绿官网首页，Hero 标题「双碳链动系统·开放智能可持续平台」。

### 1.8 异常与边界情况

| 现象 | 原因 | 处置 |
|---|---|---|
| 5173 拒绝连接 | 前端未启动 | `cd oaiss-chain-frontend && npm run dev` |

**A. 碳核算与标准类**

| 术语 | 简明解释 | 在本项目中的落点 |
|---|---|---|
| **双碳** | 「碳达峰」（排放到顶后转降）+「碳中和」（净排放归零）两个国家战略目标合称。 | 全系统业务背景 |
| **碳排放范围一/二/三（Scope 1/2/3）** | 国际通用排放分类：**范围一**=企业自己烧燃料的直接排放；**范围二**=外购电/热的间接排放；**范围三**=上下游供应链间接排放。 | 填报页三个区块按此划分 |
| **GB/T 32150** | 中国国家标准《工业企业温室气体排放核算和报告通则》，规定怎么算排放、用哪些参数。 | `PowerGenerationFormulaService` / `PowerGridFormulaService` |
| **活动数据 / 排放因子** | 排放量 = **活动数据**（用了多少燃料/电）× **排放因子**（每单位产生多少碳）。 | 填报每行两个必填数字 |
| **FC / NCV / CC / OF** | 发电行业四参数：燃料消耗量 FC、低位发热量 NCV、单位热值含碳量 CC、碳氧化率 OF。 | 碳核算公式页每个燃料分组四输入 |
| **tCO₂e** | 吨二氧化碳当量，把不同温室气体按增温潜势折算成二氧化碳的计量单位。 | 全站排放量单位 |
| **CEA** | 中国碳排放配额（China Emission Allowance），政府分配给控排企业的允许排放额度，可交易。 | 企业「碳配额」 |
| **CCER** | 国家核证自愿减排量，企业通过减排项目产生的可交易信用。 | 「碳中和项目」模块 |
| **碳币（Carbon Coin）** | 本项目内部结算代币，用于买卖配额时资金清算，**不等于真实货币**。 | 「碳币账户」页 |

**B. 区块链与安全类**

| 术语 | 简明解释 | 在本项目中的落点 |
|---|---|---|
| **联盟链存证** | 把数据哈希写进多方共维护的账本，事后任何一方单改数据都会对不上哈希。 | 报告审核通过后自动上链 |
| **哈希（Hash）** | 把任意长度内容压成固定长度「指纹」的单向函数（本项目 SHA-256）。改一字节指纹全变。 | 区块哈希、交易哈希 |
| **数字签名** | 用**私钥**对内容算签名，别人用**公钥**验证。作用：证明「是你发的」（身份）+「内容没被改」（完整性）。 | `DigitalSignatureService` |
| **RSA / SM2（国密）** | 两种非对称加密算法。RSA 是国际主流；**SM2 是中国国家商用密码标准**，政企项目常被要求支持。本项目**双轨自适应**：按公钥特征自动选算法。 | `security/crypto/RsaSignatureStrategy`、`Sm2SignatureStrategy` |
| **AES-256-GCM** | 对称加密（加解密同一把密钥），GCM 模式同时提供加密与完整性校验。用于加密存储私钥。 | `RSA_KEK` 信封加密 |
| **信封加密（Envelope Encryption）** | 用「主密钥（KEK）」加密「数据密钥」，再加密数据。轮换主密钥不必重加密全部数据。 | 私钥入库前加密 |
| **DVP（券款对付）** | Delivery versus Payment，「钱货两讫」：交割资产同时完成付款，两边原子完成。 | 撮合成交结算 |
| **自成交 / 洗售（Wash Trading）** | 同一个人自己跟自己成交，制造虚假交易量，属市场操纵，必须拦截。 | `DoubleAuctionService:240-242,348-379` |
| **CDA（连续双向拍卖）** | Continuous Double Auction：买卖持续挂单，系统按「价格优先、时间优先」实时撮合，成交价常取中间价。 | 「双向拍卖」模块 |
| **幂等（Idempotent）** | 同一操作执行一次与多次结果相同。用于「补上链」这类可重试动作，避免重复加分/重复上链。 | `certifyReport` 幂等跳过 |
| **死信（Dead Letter）** | 重试多次仍失败的消息，转入「死信」等人工处理，避免无限重试。 | `OutboxMessage` 的 `DEAD` 状态 |

### 5.1 碳核算（上传审核）`/enterprise/carbon/upload`  核心入口

#### 功能概述

企业碳报告的**全生命周期工作台**，也是企业登录后的默认首页。负责：创建报告 → 填活动数据与排放因子 → 系统自动算总量并自动签名 → 提交审核 → 查看审核结果。

#### 入口页面 / 路径

#### 涉及角色与权限

#### 关键数据与依赖

- 列表表头（实测）：报告编号 / 报告标题 / 核算周期 / 总排放量(tCO2e)ⓘ / 状态 / 签名ⓘ / 审核人 / 创建时间 / 操作
- 顶部创建区：报告标题输入框 + 核算周期 + 【创建】按钮
- 行操作：查看详情 / 提交 / 删除

### 5.3 双向拍卖 `/enterprise/trading/market`  技术亮点页

#### 功能概述

碳配额**双向连续竞价拍卖（CDA）**交易大厅。买方出价、卖方要价，系统按价格优先+时间优先撮合，匿名成交。页面还嵌入了 AI 履约采购建议。

#### 入口页面 / 路径

`/enterprise/trading/market`（侧边栏 碳交易▾ → 双向拍卖）

#### 涉及角色与权限

- 查看与挂单：ENTERPRISE（`POST /auction/buy`、`POST /auction/sell` 均 `hasRole('ENTERPRISE')`）
- **触发撮合：仅 ADMIN**（`POST /auction/match` 为 `@PreAuthorize("hasRole('ADMIN')")`）——这点极易误判，务必注意：企业用户点不到也不能触发撮合。

#### 关键数据与依赖

- 页签（实测）：全部挂单 / 我的挂单 / 撮合结果
- 表头（实测）：序号 / 买卖方向 / 数量（吨）/ 价格（元/吨）/ 状态 / 创建时间
- 按钮：查询 / 创建订单（每行有勾选框，支持批量）
- AI 建议区：「AI 智能履约决策建议（基于企业核算缺口）」，需 `POST /copilot/procurement-advice`
- 接口：`POST /auction/buy`、`POST /auction/sell`、`POST /auction/match`、`GET /auction/orders`、`GET /auction/my-orders`、`GET /auction/results`
- 实测分页总数：**42 条**（分页控件），当前在挂单 36 笔

#### 术语解释

- **买卖方向**：`1` 买 / `2` 卖（订单号前缀 `B`=买、`S`=卖）。
- **待撮合 / 完全匹配 / 部分匹配**：`AuctionOrderStatusEnum` 的 `0/2/1`。
- **成交价取中间价**：`settlementPrice = (买价 + 卖价) / 2`（源码 `DoubleAuctionService` 类注释第 56 行）。
- **买方冻结资金 + 差价退回**：挂买单时按挂单价冻结碳币；若最终成交价更低，系统自动退回差额 `(买价-成交价)×成交量`（`DoubleAuctionService:275-279`）。
- **自成交/洗售防范**：同一用户存在未完成的反向挂单时，禁止提交同向新单（`DoubleAuctionService:94-97,137-140`），撮合时也会跳过同一主体的买卖配对（`:240-242`）。

#### 实操校验步骤

1. 进入 `/enterprise/trading/market`，关闭可能出现的引导弹窗。
2. 观察页面顶部：是否有「AI 智能履约决策建议」卡片及其文字内容。
3. 切到「我的挂单」页签，查看现有挂单。
4. 点【创建订单】，尝试提交一笔买单（数量 2、价格 30）。
5. 记录提交前后的「碳币账户」冻结余额（另开一页看 `/enterprise/carbon-coin/account`）。
6. 用 `admin` 账号调用 `POST /api/v1/auction/match` 触发撮合。
7. 查看「撮合结果」页签。

#### 预期结果

- 步骤 2：应能看到 AI 建议卡片，文案形如「【履约高风险警报】当前企业碳排放量…建议立即启动分期采购，避开履约期临近时的全网集中抢购…」。**本次实测该接口已返回 200（旧版为 401）**。
- 步骤 3：能看到本企业挂单，状态含「待撮合」「完全匹配」等。
- 步骤 4 ⚠️ **可能被业务规则拒绝**：实测当前环境会返回 `400`，提示「存在未完成的卖出挂单，同一主体禁止同时买卖以防自成交/洗售交易」。这是**正确的风控行为**，不是 bug。要真正下单成功，需先撤销反向挂单或用另一个无反向挂单的企业账户。
- 步骤 5：若下单成功，冻结余额应**增加**（增加量 = 数量 × 挂单价）；若被步骤 4 规则拒绝，则余额不变（实测 delta = 0）。
- 步骤 6：ADMIN 调用返回 `200 操作成功`；本次实测 `matches created: 0`，因为**当前 36 笔在挂单全部属于同一用户（user_id=2）**，被自成交防范全部跳过（已用 SQL 核实：`SELECT user_id,COUNT(*) FROM auction_order WHERE status IN (0,1) GROUP BY user_id` → 只有 `2 → 36`）。
- 步骤 7：「撮合结果」页签当前为空（与步骤 6 的 0 条匹配一致）。

#### 异常与边界情况

| 现象 | 原因 | 说明 |
|---|---|---|
| **表头提示显示「共 0 条」但表格有 10 行、分页显示「共 42 条」** | **真实缺陷 D-01**：`TradingMarket.vue:388` 把 `selectedRows.length`（当前勾选行数）当作总数渲染，而应使用 `total` | 实测证据：`.table-tip` 文本「共 0 条」、`.el-pagination__total` 文本「共 42 条」、表格 10 行 |

| 下单报「禁止同时买卖」 | 自成交防范规则命中 | 属正确风控 |
| AI 建议不出现 | 若 ML 服务或密钥异常，代理会返回错误 | 本次实测正常；异常时见 D-03 历史记录 |

### 5.14 碳核算公式 `/enterprise/carbon-formula`  国标落地页

#### 功能概述

GB/T 32150 国标核算模型的**在线计算器**。分「发电行业」与「电网行业」两套模型，输入参数即出排放量。这是全项目的**技术底座**，也是理解「排放量怎么来的」最直观的地方。

#### 入口页面 / 路径

`/enterprise/carbon-formula`（侧边栏 碳中和▾ → 碳核算公式）

#### 涉及角色与权限

`hasRole('ENTERPRISE')`（`CarbonController` 的 `calculate` 系列端点）。

#### 关键数据与依赖

- 页签（实测）：发电行业 / 电网行业
- 通用输入：报告年份、企业名称
- 发电行业：按燃料分组折叠面板（实测「原煤 / 洗精煤 / 其他洗煤 / 型煤 / 其他煤制品」），每组四个参数：**燃料消耗量 (FC)**、**低位发热量 (NCV)**、**含碳量 (CC)**、**碳氧化率 (OF)**，每个参数旁有【实测反推】按钮；下方「脱硫过程排放」：碳酸盐消耗量 / 脱硫排放因子 / 脱硫转化率
- 电网行业输入（实测封装）：输送电量 / 线损率 / 电网排放因子 / 发电量 / 购入电量 / 输出电量 / 购入电力排放因子
- 按钮：国标法规智囊 Copilot / 载入火电机组典型样本 / 载入电网输配电典型样本 / 计算 / 实测反推
- 接口：`POST /carbon/calculate/power-generation`、`POST /carbon/calculate/power-grid`、`POST /carbon/calculate/power-generation/oxidation-rate`；Copilot 走 `POST /copilot/policy-qa`

#### 术语解释

- **国标核算公式（发电行业）**：`排放量 = FC × NCV × CC × OF × 44/12`。其中 44/12 是碳（C，原子量 12）转二氧化碳（CO₂，分子量 44）的换算系数。
- **低位发热量（NCV）**：燃料完全燃烧后其水蒸气保持气态时释放的热量，国标统一用低位。
- **碳氧化率（OF）**：燃料中的碳实际被氧化的比例（不是全部碳都烧掉）。
- **实测反推**：当现场测不到某个参数（如 CC），但能测到总排放量时，用总排放量反算该参数。这是工程上很实用的功能。
- **脱硫过程排放**：脱硫工艺中碳酸盐分解产生的额外 CO₂。
- **电网排放因子**：每消耗 1 MWh 外购电对应的 CO₂ 排放量，随区域电网结构变化。

#### 实操校验步骤

1. 进入 `/enterprise/carbon-formula`。
2. 在「发电行业」页签，点【载入火电机组典型样本】，观察各参数被自动填充。
3. 手工修改「原煤」组的「燃料消耗量 (FC)」为一个新值。
4. 点【计算】，读取结果。
5. 点某个参数旁的【实测反推】，观察交互。
6. 切「电网行业」，点【载入电网输配电典型样本】→【计算】。
7. 点右上角【国标法规智囊 Copilot】，在抽屉中提问「GB/T 32150 发电企业核算边界是什么?」。

#### 预期结果

- 步骤 2：四个参数（FC/NCV/CC/OF）自动填入国标默认/典型值。
- 步骤 4：输出该燃料的排放量及各范围小计；页面「小计」区域显示合计 tCO2e。
- 步骤 5：弹出输入引导，让你输入已知排放量以反算参数。
- 步骤 6：电网模型输出输电/线损相关排放结果。
- 步骤 7：**Copilot 抽屉返回中文专业回答**。实测响应示例：「根据国家标准《GB/T 32150 工业企业温室气体排放核算和报告通则》，企业进行碳核算时须遵循『完整性、准确性、一致性、透明度』四大原则。建议优先核实企业边界（厂区红线内固定设施）、燃料入厂与入炉计量化验台账，并保留至少 5 年原始凭单备查。」并返回 `relevant_standards: ["GB/T 32150-2015 工业企业温室气体排放核算和报告通则"]`、`model_used`。⚠️ **旧版本此处 401 失败，现已修复**。

#### 术语解释

- **验签**：用企业公钥验证报告签名的有效性。验签失败意味着报告内容在签名后被改动过（或签名本身伪造），**必须驳回**。
- **审核回避原则**：审核员不能审核本企业提交的报告（源码 `CarbonService.java:150` 抛「审核回避原则：禁止审核本企业提交的碳报告」）。
- **方案 A（自动上链）**：审核员点「通过」后，系统在同一业务流程内自动把报告提交到 Fabric，成功则状态直接变为「已上链」，无需第二道人工核准。

4. 查看弹窗中是否展示企业提交的 Scope1/2/3 明细与验签结果。
5. 填写审核意见，点【通过】。
6. 观察提示与状态变化。
7. 到「审核历史」确认该报告记录。

#### 预期结果

- 步骤 2：待审 6 条；「验签」列显示验签状态（实测存量报告多为「已签名」/无签名）。
- 步骤 3：弹出审核对话框，含报告明细与「通过 / 驳回」两个决策。
- 步骤 5：接口 `POST /api/v1/carbon/review` 返回 **200 / message「审核完成」**。
- 步骤 6 ⭐ **关键**：响应中 `status` 直接变为 **5（已上链）**，并返回 `blockchainTxHash`（实测 `543684bbe5f1306c...`）、`onChainAt` 时间戳、`signatureValid: true`。这说明**自动上链已生效**。

#### 异常与边界情况

| 现象 | 原因（源码位置） |
|---|---|
| 提示「数字签名校验失败…禁止审核通过」 | 验签失败时禁止通过（`CarbonService.java:158-160`）。这是**核心防篡改逻辑**，不是 bug |

企业 `/enterprise/carbon/upload` → 审核员 `/auditor/audit/list` → 企业 `/enterprise/blockchain/browser` → 企业 `/enterprise/credit/score`

#### 涉及角色与权限

ENTERPRISE（创建/提交/查看）+ REVIEWER（审核，触发自动上链）。

#### 关键数据与依赖

- 状态机（`ReportStatusEnum`）：`0 草稿 → 1 已提交 → 3 审核通过 → 5 已上链`，或 `→ 4 审核拒绝`
- **关键：审核通过后自动上链，成功则直接跳 5，不经过人工核准**（`CarbonService.autoCommitToChain`）
- 上链失败则停在 3，由「上链补救」页重试（`CarbonService.java:187-209`）
- 信用分副作用：审核通过 +5（`applyApprovedReportSideEffects`）；驳回 −10 或验签失败 −20

#### 术语解释

- 见第 2 章（数字签名、联盟链存证、幂等、事务性发件箱）。

#### 实操校验步骤（逐步照做）

**阶段 A：企业填报**
1. `enterprise001` 登录 → `/enterprise/carbon/upload` → 关引导弹窗。
2. 填标题与核算周期 → 【创建】→ 对话框内填「范围一」活动数据 `100`、排放因子 `2.5` → 【创建】。
3. 记下列表首行的**报告编号**与**总排放量（应为 250）**。
4. 点该行【提交】。

**阶段 B：审核员审核（触发自动上链）**
5. 换 `reviewer001` 登录 → `/auditor/audit/list`。
6. 找到刚提交的报告，点【审核】。
7. 确认验签状态正常，填审核意见，点【通过】。
8. 记录返回的状态与交易哈希。

**阶段 C：验证上链**
9. 换回 `enterprise001` → `/enterprise/blockchain/browser` → 「交易记录」页签。
10. 用步骤 8 的交易哈希在页面【查询交易】，或用接口 `GET /api/v1/blockchain/transaction/{txHash}`。
11. 调 `GET /api/v1/blockchain/status` 确认 `mode`。

**阶段 D：验证信用分**
12. 进入 `/enterprise/credit/score`。
13. 查看「评分历史」最新一条。

#### 预期结果（本次实测原样记录）

### 9.2 链路二：配额交易与结算（企业 ↔ 企业 + 管理员触发撮合）

#### 功能概述

碳配额从「挂单 → 撮合 → 结算 → 碳币划转」的完整资金/资产流转。核心难点是**防超卖、防自成交、差价退回**。

#### 入口页面 / 路径

企业 `/enterprise/trading/market`（挂单）→ 管理员接口 `/api/v1/auction/match`（触发撮合）→ 企业 `/enterprise/orders/manage`（看成交）+ `/enterprise/carbon-coin/account`（看资金）

#### 涉及角色与权限

| 动作 | 角色 | 接口 |
|---|---|---|
| 挂买单/卖单 | ENTERPRISE | `POST /auction/buy`、`POST /auction/sell` |
| 触发撮合 | **仅 ADMIN** | `POST /auction/match` |
| 查看挂单/结果 | 四角色 | `GET /auction/orders`、`/my-orders`、`/results` |

#### 关键数据与依赖

- 撮合规则：价格优先 + 时间优先；买价 ≥ 卖价可成交；成交价 = 买卖中间价
- 资金锁定：挂单即冻结（买单冻碳币、卖单冻配额），成交才扣，撤单/差价退回解冻
- 并发保护：`@DistributedLock(key="'auction:matching'")` 全局串行，防超卖
- 自成交防范：同主体存在未完成反向单时禁止提交同向单；撮合时跳过同主体配对
- 数据表：`auction_order`、`matching_result`、`transaction`、`carbon_coin_account`

#### 术语解释

- 见第 2 章（CDA、DVP、自成交/洗售、分布式锁）。

#### 实操校验步骤

1. **确认账户干净**：用 `enterprise001` 访问 `GET /api/v1/auction/my-orders`，确认没有未完成的**反向**挂单（否则第 2 步会被风控拒绝）。
2. 挂买单：`POST /api/v1/auction/buy`，body `{"direction":1,"quantity":2,"price":30}`。
3. 记录返回的 orderNo 与订单状态。
4. 查碳币账户：`GET /api/v1/carbon-coin/account`，对比挂单前后的 `balance` / `frozenBalance`。
5. 用 `admin` 触发撮合：`POST /api/v1/auction/match`（body `{}`）。
6. 查撮合结果：`GET /api/v1/auction/results`。
7. 查配额变化：`GET /api/v1/enterprise/quota`。

#### 预期结果

- 步骤 1：若已有未完成卖单，`POST` 会返回 **400**，消息「存在未完成的卖出挂单，同一主体禁止同时买卖以防自成交/洗售交易」——**这是正确的风控，不是故障**。
- 步骤 2：成功时返回 orderNo（形如 `B202610221030001`）、方向=买、数量、价格、状态「待匹配」（`0`）。
- 步骤 4：**冻结余额增加**（增加量 = 2 × 30 = 60），`balance` 减少或不变（取决于实现扣减时机）。
- 步骤 5：ADMIN 调用返回 **200「操作成功」**；企业调用则 **403 error.permission.denied**（实测）。
- 步骤 6：若存在**不同用户**的匹配买卖单，则生成 `matching_result` 记录（`statusText` 待结算/已结算），并按中间价结算。
  ⚠️ **本次实测例外**：返回 `matches created: 0`，因为当时 36 笔在挂单**全部属于同一用户**（SQL 核实 `user_id=2 → 36`），被自成交防范全部跳过。这是**数据状态导致，不是撮合引擎故障**。
- 步骤 7：成交后买方配额增加、卖方配额减少。

#### 异常与边界情况

| 现象 | 原因 | 处置 |
|---|---|---|
| 撮合总是 0 条 | 挂单集中在同一用户，自成交全被跳过 | 用**两个不同企业账号**分别挂买/卖单再撮合 |
| 企业无法触发撮合 | `POST /auction/match` 仅 ADMIN | 属权限设计；如产品上不期望如此，属 D-06 待讨论项 |
| 挂单后余额没冻结 | 可能余额不足或被风控拦截 | 查返回码与 `frozenBalance` |
| 成交价与挂单价不同 | 取中间价，属正常 | 关注差价是否已退回买方 |

### 9.4 补充：如何做有效的越权校验（安全边界验证）

#### 功能概述

前端路由守卫只是体验层，**真正的安全边界在后端**。本节给出可直接照做的越权测试方法。

#### 入口页面 / 路径

不涉及页面，直接调 REST 接口。

#### 涉及角色与权限

全部四角色交叉测试。

#### 关键数据与依赖

- 认证方式：请求头 `Authorization: Bearer <accessToken>`
- 鉴权：`JwtAuthenticationFilter` 解析 → `SecurityConfig` 的 `@PreAuthorize` 判定
- 数据隔离：`@DataIsolation` 切面按 `enterpriseId` 自动加条件

#### 术语解释

- **越权（水平/垂直）**：水平越权 = 同角色看别人数据；垂直越权 = 低权限角色调高权限接口。
- **数据隔离（Data Isolation）**：框架层自动把查询限定在「当前用户所属企业」，防止水平越权。

#### 实操校验步骤

1. 用 `enterprise001` 登录拿 Token，调用 `POST /api/v1/auction/match`。
2. 用 `enterprise001` 的 Token 调用 `GET /api/v1/admin/users`。
3. 用 `reviewer001` 的 Token 调用 `POST /api/v1/carbon/reports`（创建报告）。
4. 用 `thirdparty001` 的 Token 调用 `POST /api/v1/carbon/review`（审核报告）。
5. 用 `enterprise001` 的 Token 调用 `GET /api/v1/credit/{别的enterpriseId}`。

#### 预期结果

| 步骤 | 预期 | 实测参考 |
|---|---|---|
| 1 | **403** | 实测 `403 code 2004 error.permission.denied` |
| 2 | **403** | 应为权限拒绝（`AdminController` 全类 `hasRole(ADMIN)`） |
| 3 | **403** | 创建报告为 `hasRole(ENTERPRISE)`；实测创建成功为 `POST /carbon/reports` 企业专属 |
| 4 | **403** | 审核为 `hasRole(REVIEWER)` |
| 5 | 只读他人信用分或 **403** | 按 `CreditScoreController` 权限设计 |

#### 异常与边界情况

| 现象 | 说明 |
|---|---|
| 返回 401 而非 403 | Token 缺失/过期，先确认能正常携带 Token |
| 返回 200 但有数据 | 可能是公开接口（如排行榜），需看业务语义再判定是否越权 |
| 前端能点但接口 403 | 前端菜单/按钮权限与后端不一致，属缺陷需登记 |

## 第 10 章 缺陷与差异清单（含复现步骤）

### 10.1 P1 · 高（业务数据看起来不对，影响对外可信度）

#### 缺陷 D-01：双向拍卖页「共 N 条」计数错误 —— ✅ 已于 2026-10-22 修复

- **原现象**：`/enterprise/trading/market` 页表头上方文本显示「共 0 条」，但同页分页控件显示「共 42 条」，且表格有 10 行数据。
- **修复后实测（2026-10-22 下午）**：`TradingMarket.vue:388` 已改为 `{{ t('common.total', { count: total }) }}`；浏览器实测 `.table-tip` = **「共 42 条」**，与分页控件**完全一致**；切「我的挂单」页签后两处同为「共 41 条」。单元测试 `src/views/__tests__/TradingMarket.test.ts` **6/6 通过**（含针对本缺陷的防退化专项断言）。
- **复现步骤**：进入 `/enterprise/trading/market` → 对比 `.table-tip` 文本与 `.el-pagination__total` 文本。
- **实测证据**：`.table-tip` = 「共 0 条」；`.el-pagination__total` = 「共 42 条」；表格行数 = 10。
- **可能原因**：`oaiss-chain-frontend/src/views/enterprise/TradingMarket.vue:388` 使用 `t('common.total', { count: selectedRows.length })`，把**当前勾选行数**当成**总记录数**渲染，应使用 `total` 变量。
- **影响**：用户会误以为没有数据；演示时非常扎眼。
- **建议**：把 `selectedRows.length` 改为 `total`；若该行本意是「已选 N 条」，则应改文案为「已选 N 条」以避免与分页总数语义冲突。

#### 缺陷 D-02：信用事件历史仍有大量英文描述残留

- **现象**：`/enterprise/credit/score` 的「评分历史」部分历史行「原因」列显示英文，如 `Deduction toward WARNING`、`Score recovery test`、`x`。
- **实测数据**：数据库 `credit_event` 共 223 条，其中**英文 171 条、中文 52 条**。
- **复现步骤**：执行 SQL — `SELECT CASE WHEN LEFT(event_description,1) REGEXP BINARY '^[A-Za-z]' THEN 'EN' ELSE 'ZH' END AS lang, COUNT(*) FROM credit_event GROUP BY lang;`
- **原因**：V14 迁移只本地化了两类**生产代码生成**的文案（认证奖励、审核驳回），**有意跳过**测试/压测造数（迁移脚本注释已说明）。
- **影响**：新产生的记录已全部中文（实测验证），但历史数据仍混杂。演示时若翻到旧记录会被看到。
- **建议**：① 演示前用演示账号产生新记录；② 清理或标注测试数据；③ 长期应把 `event_description` 改为「事件类型枚举 + 参数」，由前端 i18n 渲染，而非存文案本身。

#### 缺陷 D-03：企业用户无法触发拍卖撮合（产品语义待商榷）

- **现象**：企业用户在「双向拍卖」大厅只能挂单，无法触发撮合；`POST /auction/match` 仅 ADMIN 可调。
- **实测**：企业调用返回 `403 error.permission.denied`；ADMIN 调用返回 `200 操作成功`。
- **复现步骤**：用 `enterprise001` Token 调 `POST /api/v1/auction/match`。
- **原因**：`DoubleAuctionController:104` 为 `@PreAuthorize("hasRole('ADMIN')")`（源码设计如此，非 bug）。
- **影响**：从「安全」角度合理（防任意用户触发全市场出清），但从「产品」角度，拍卖大厅通常应自动撮合或有明确触发者说明。
- **建议**：① 增加定时任务自动撮合；② 在前端明示「撮合由管理员统一发起」；③ 在文档中说明该设计意图。

### 10.2 P2 · 中（体验 / 一致性 / 可维护性）

#### 缺陷 D-04：监管角色职责与文档不一致

### 11.6 本地自动化登录方法（仅测试环境）

由于登录需要图形验证码，自动化巡检可采用以下方式（**生产环境严禁**）：

1. 请求 `GET /api/v1/captcha/generate` 拿到 `captchaKey`。
2. 从 Redis 读出明文验证码：`docker exec oaiss-redis redis-cli -a <REDIS_PASSWORD> --no-auth-warning GET captcha:<captchaKey>`。
3. 携带 `captchaKey` + 明文验证码调用 `POST /api/v1/auth/login`。
4. 拿到 `accessToken` 后，注入前端 `localStorage.access_token` 即可跳过 UI 登录直接访问受保护页面。

> 该方法利用的是「本地可访问 Redis」这一测试环境特性，**应用侧验证码校验逻辑未被绕过**，不影响安全结论。
