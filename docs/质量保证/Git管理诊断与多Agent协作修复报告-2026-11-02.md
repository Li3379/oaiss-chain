# Git 管理体系与多 Agent 并发协作 —— 诊断修复报告

- **日期**：2026-11-02
- **范围**：CI/CD、提交与分支规范、版本化管理、多 Agent 并发防冲突
- **结论**：CI 从「连续 10 次 main 全红」转为**全绿（12 通过 / 0 失败）**；建立三道本地护栏 + 路径租约；版本号三方对齐；分支保护生效。
- **关联 PR**：[#1](https://github.com/Li3379/oaiss-chain/pull/1)（已 squash 合并为 `9058d6c`）

---

## 一、诊断结论：根因不是代码坏，是三类机制缺失

| # | 现象 | 真实根因 |
|---|---|---|
| 1 | CI 连续 10 次 main 全红 | **文档跑在代码前面**：已推送的 `DEV-GUIDE §11` 写 163 端点 + V22 迁移，推送的代码只有 161 端点、且没有 V22。多出来的部分全在**另一个会话的未提交工作区**里 |
| 2 | 分支上一切正常，合进 main 才红 | `lint.yml` **只监听 main**。`feat/*` 推送时不跑任何检查 |
| 3 | 「Java (PMD + SpotBugs)」长期显示绿色 | `mvn pmd:check \|\| true`。pom 里 `failOnViolation=false` 已让 mvn 返回 0，再叠 `\|\| true` = **永远成功**。假绿比不接更糟：它阻止别人去接真的 |
| 4 | 后端 174 个测试类从未在 CI 跑过 | 流水线里根本没有 `mvn test` |

### 一次真实的并发事故（本报告的核心动因）

```
19:47  会话 B  提交并推送  V23__update_unit_price_comment.sql
19:50  会话 A  新建        V22__add_credit_delisted.sql   （未提交）
```

两个会话共享同一个工作目录，彼此「看不见」对方的意图。
V22 排在 V23 之后入库 → Flyway 判定 out-of-order → **已部署环境拒绝启动**。

`git status` 对此无能为力：它只说「有改动」，说不出谁在改、改到哪一步、还要多久。

## 二、修复清单

### 2.1 止血：并发遗留与版本号倒挂

| 项 | 处置 |
|---|---|
| V22 迟到的迁移 | **重编为 V24**。绝不补 V22——V23 已在部分环境落库，补号会让这些环境拒启动 |
| `DEV-GUIDE §11` | 迁移行改为 `V1-V24`，**V3/V22 声明为空号**，共 22 个版本 |
| `doc-verify` 门禁 | 原只硬编码识别 V3，空号被判红，逼人二选一：放宽断言（失去保护）或补 V22（真炸库）。改为**声明式空号 + 双向断言**（声明了就必须真的没有文件） |
| 未提交的 R-03 工作 | 补完并提交（`ea38f09`）：`delisted` 字段、delist/repeal 端点、受限名单公示 Tab |
| 类型错误 2 处 | 修复后 `vue-tsc` 0 错 |

> 门禁改动做了**正反向验证**：声明 V24 为空号 → 正确报「声明为空号但文件存在」；恢复后 → 通过。

### 2.2 CI 流水线

| 缺陷 | 修复 |
|---|---|
| 触发面只有 main | `push: ['**']` 跑快速门禁（~2 min）；PR 与 main 加跑单测。分支过滤放在 job 内 `if`，避免分支改名就静默失效 |
| `\|\| true` 假绿 | **棘轮（ratchet）**：428 条 PMD / 166 条 SpotBugs 写入基线，一条都不许多；修掉的用 `--update` 收紧 |
| 测试缺位 | 新增 `Backend Unit Tests` / `Frontend Unit Tests` / `ML Service Tests` 三个 job |
| 4 个孤儿门禁 | `workflow-verify`、`jpa-schema-verify`、`quota-ledger-verify`、`image-availability-verify` 全部接入，按 job 汇总失败项（串联会让一轮只暴露一个问题） |

**棘轮为什么不直接开 `failOnViolation`**：存量数百条告警会让所有 PR 立刻堵死，团队第一反应必然是再加一个 `|| true`，回到原点，还多一层「我们试过了」的错觉。棘轮是「存量不阻塞、增量不放松、方向单向下行」。

### 2.3 提交与分支规范

| 机制 | 位置 | 说明 |
|---|---|---|
| Conventional Commits | `.githooks/commit-msg` | 实测最近 300 条提交 **100% 合规**——缺的不是习惯，是护栏。放行 `Merge`/`Revert`/`fixup!`/`squash!` |
| 禁直推 main | `.githooks/pre-push` | `ALLOW_PUSH_MAIN=1` 可显式豁免（紧急回滚场景） |
| Flyway 水位线 | `.githooks/pre-push` | 新增迁移版本号必须 > `origin/main` 最大值。**已用真实场景验证**：造一个迟到的 V22 → 正确拦下并给出改号指引 |
| 提交信息复查 | `.githooks/pre-push` | `commit-msg` 只在新建提交时跑；rebase/amend 后需要复查 |
| 分支保护 | GitHub | `strict`（需与 main 同步）+ 8 个必需检查 + 禁 force push + 禁删除 |

**`pre-push` 刻意不跑测试**：同步阻塞 15 分钟的结果是人人都加 `--no-verify`。测试在 CI。

### 2.4 多 Agent 并发防冲突

三道机制，对应三种失效形态：

1. **隔离**：一个任务 = 一个分支 = 一个 worktree
   （同一目录切分支会让另一个会话的未提交改动「跟着漂移」）
2. **声明**：`scripts/agent/lease.mjs` 路径租约
   硬冲突（前缀重叠）拒绝 / 软冲突（同目录不同文件）警告 / 默认 120 分钟到期可续租
3. **契约**：`docs/开发手册/多Agent协作-Git契约.md`
   含高危冲突路径矩阵与完整作业流程

> 租约目录**不入库**：用版本控制管理锁是反模式——每次抢锁都产生提交，合并时互相冲突。

**高危冲突路径矩阵**（历史修改频率 Top，需独占）：

| 路径 | 冲突原因 |
|---|---|
| `db/migration/` | 版本号必须全局唯一递增 |
| `i18n/locales/zh-CN.ts` + `en-US.ts` | 两个巨型对象字面量，任何两处文案改动都会撞行 |
| `DEV-GUIDE.md` | §11 事实表是全仓汇总数字 |
| `config/menu.ts` / `layout/index.vue` / `style.css` | 改一处全站受影响 |
| `CarbonService.java` | 核心业务，多任务高频触碰 |

### 2.5 版本化

诊断发现四处版本号互不相干，**全部不可信**：

```
pom.xml / oaiss-chain-backend/pom.xml    1.0.0
oaiss-chain-frontend/package.json        0.0.0   ← Vite 脚手架默认值，从未改过
CHANGELOG.md                             1.7.1   ← 唯一持续维护的
```

后果：把 1.7.1 的镜像当 1.0.0 发布、按 `package.json` 判断前端版本，都会得到错误结论。

- `scripts/gates/version-verify.mjs`：以 CHANGELOG 为唯一事实源（它记录版本语义），强制三方对齐；附加 SemVer 合法性、版本段顺序单调、已打 tag 必须有对应段落
- `scripts/release.mjs`：发布前置 7 项检查（版本递增 / CHANGELOG 非占位 / 版本门禁 / 在 main / 工作区干净 / 不落后远端 / 当前提交 CI 全绿 / tag 未占用）。**默认干跑**，`--tag`/`--push` 显式触发

版本号统一至 **1.7.1**。

### 3.2 CI 首次运行抓到的真实缺陷

`Backend Unit Tests` 首次运行即失败，且**不是环境噪音**：

```
FabricGatewayConfigTest.resolveResource_shouldSupportClasspathAndAbsolutePaths
  → assertTrue(classpathResource.exists()) 失败
FabricGatewayConfigTest.fabricGateway_whenCaEnabledAndEnrollmentSucceeds_usesCaIdentity
  → NullPointerException: getResourceAsStream("fabric/crypto/user-cert.pem") is null
```

根因：`fabric/crypto/` 是 `scripts/ops/generate-fabric-crypto.sh` 的**运行时产物**，被 `.gitignore:54` 排除，干净克隆上根本不存在。本地一直绿是因为开发者跑过生成脚本、`target/classes` 里残留旧文件——典型的**本地绿 / CI 红**。

修复方式：用 BouncyCastle 现场自签临时证书；`exists()` 断言只保留在测试自建的临时文件上。
**没有**给测试加 `@Disabled`，也**没有**把私钥入库削弱安全设计。

验证：把 `src/main/resources/fabric/crypto` 与 `target/classes/fabric/crypto` 整个移走后重跑 → **7/7 通过**（修复前必红）。

### 3.3 顺带修复的 5 条 SpotBugs High

既然接了静态分析，就把 High 一次清掉（`166 → 161`，High `5 → 0`）：

| 位置 | 缺陷 | 说明 |
|---|---|---|
| `EnterpriseContextHolder.isAdmin/isEnterpriseUser/isReviewer` | `Integer == Integer` | 实际比引用。当前枚举值落在 -128..127 缓存区间所以碰巧正确，**但这类代码一旦状态码超出缓存就会静默失效** |
| `DoubleAuctionService.cancelOrder` | 同上 | **撤单闸门**：状态判断失效意味着已成交订单可被撤销 |
| `ApiVersionConfig.SUPPORTED_VERSIONS` | `public static final String[]` | `final` 只锁引用，内容仍可被任何调用方改写 → 版本协商会静默接受未实现的版本。改为 `List.of()` + 新增不可变性测试 |

## 五、快速命令卡

```bash
# 一次性安装护栏
git config core.hooksPath .githooks

# 开工
git fetch origin && git worktree add ../t-<id> -b feat/<slug> origin/main && cd ../t-<id>
node scripts/agent/lease.mjs acquire --task "feat/<slug>" --paths "<dirs>"

# 自检
node scripts/gates/doc-verify.mjs && npm run type-check --prefix oaiss-chain-frontend

# 交付
git push -u origin feat/<slug> && gh pr create --fill && gh pr checks --watch

# 收尾
node scripts/agent/lease.mjs release --task "feat/<slug>"
gh pr merge --squash --delete-branch && git worktree remove ../t-<id>

# 发布
node scripts/release.mjs 1.7.2            # 干跑
node scripts/release.mjs 1.7.2 --tag --push
```
