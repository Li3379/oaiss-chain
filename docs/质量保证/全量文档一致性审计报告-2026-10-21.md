## 一、结论摘要

「意愿一致」的答案是：**不一致，而且是多层不一致**。

| 类别 | 数量 | 严重度 |
|---|---|---|
| ① 文档间职责归属相互冲突 | 5 处（涉及 8 份文档） | 高 |
| ② 文档内部自我矛盾 | 2 份文档 | 高 |
| ③ 数字事实与代码实测不符 | 6 份文档 | 中 |
| ④ 原始需求本身存在双表述 | 1 处（核心） | 高 |

**最关键的发现**：原始需求（L1）**内部就不是单一口径**——它同时写了「审核员铸造并上链」和「管理员作为提交对等节点，在上链前再次审查」，还写了「系统后台自动将该报告进行上链」。所以下游文档各抄一半，才出现今天的分裂。**这不是执行层抄错，是源头就有三种表述没收敛。**

## 三、① 文档间职责归属冲突（5 处）

### 冲突 C-1：「谁执行上链」——多份权威文档多种说法

| 文档 | 等级 | 原文 | 归属 |
|---|---|---|---|
| docs/raw 原始需求 | L1 | 「验证通过后，**数据审核员**为该企业提供碳排放报告，并将企业碳报告进行**铸造和上链**」 | REVIEWER |
| docs/raw 原始需求 | L1 | 「提交对等节点即**管理员**在确认无误后将交易区块上链」 | ADMIN |
| docs/raw 原始需求 | L1 | 「管理员作为提交对等节点，可在信息**上链前再次审查**碳核算数据」 | ADMIN |
| docs/raw 原始需求 | L1 | 「当数据审核员点击提交碳排放报告后，系统后台**自动**将该报告进行上链」 | 系统自动 |
| 系统设计与架构规格书 §4.3 | L2 | 「验证通过后，**数据审核员**……铸造和上链」 | REVIEWER |
| 系统设计与架构规格书 §3.2 表7 | L2 | 「数据审核（RSA验签+上链）」→ 仅审核员 √ | REVIEWER |
| 毕业设计成果(企软方向) | L3 | 「**第三方监管机构**对审核结论执行最终合规确认，通过后……完成报告哈希上链」 | THIRD_PARTY |
| 技术架构与使用说明书 | L4 | 「**第三方监管与上链**：监管机构确认后……提交至账本」 | THIRD_PARTY |
| **代码实现** | — | CarbonController.java:238 `@PreAuthorize("hasRole('ADMIN')")` | ADMIN |

**判定**：
- **L1 自身就有三种表述**（审核员上链 / 管理员上链前审查 / 系统自动），未收敛。
- L2 采纳了「审核员」这一支。
- L3、L4 采纳了「第三方监管」——**这在 L1 中找不到任何依据**，是 L1 之后凭空引入的。
- 代码实现落在「管理员」，与 L1 的第二支吻合，但与 L2 冲突。

### 冲突 C-2：第三方监管是「只读监督」还是「流程内审批」

| 文档 | 原文 | 定位 |
|---|---|---|
| docs/raw L1 | 「第三方监管机构可作为特殊的参与者角色，进行数据的**定期核查**」 | 只读 |
| docs/raw L1 | 「**拥有访问**特定交易信息的权限」 | 只读 |
| 设计规格书 §3.1 | 「监管碳报告和交易数据，**查看**统计信息，**定期核查**」 | 只读 |
| 设计规格书 §4.14 | 「提供监管视角的碳报告**查询**、监管统计和机构信息管理」 | 只读 |
| 毕业设计成果 用例表 | 「监管账户具备**只读监管权限**」「监管操作**全程只读留痕**，不产生业务数据变更」 | 只读 |
| 毕业设计成果 §1.2.3（同文档） | 「**监管确认与上链**：第三方监管机构对审核结论执行**最终合规确认**」 | 审批 |
| 技术架构与使用说明书 | 「**最终上链存证确认**」 | 审批 |
| 认知与操作教学手册 | 「⑤**监管核准上链**」「监管决定**上不上链**」 | 审批 |

**判定**：**L1 + L2 + 毕业设计成果用例表（多处处独立）都说监管只读**；只有毕业设计成果另一节、L4、认知手册说监管审批。**以 L1 为准 → 监管只读，无审批权。**

### 冲突 C-3：毕业设计成果.docx 自我矛盾（同一文档内）

| 位置 | 表述 | 冲突 |
|---|---|---|
| §1.2.3 步骤(4) | 「监管确认与上链：**第三方监管机构**对审核结论执行最终合规确认，通过后……完成报告哈希上链」 | 监管 = 上链触发者 |
| 同文档用例表 | 「参与者：**第三方监管机构**……补充说明：**监管操作全程只读留痕，不产生业务数据变更**」 | 监管 = 只读 |
| §1.2.1 步骤(2) | 「第三方监管拥有**穿透式只读监管权限**」 | 监管 = 只读 |

**同一份毕业设计成果文档，三处对监管的定位互相打架。这是答辩时最容易被问住的地方。**

### 冲突 C-4：设计规格书权限矩阵与自身角色表矛盾

§3.2 表7 把「执行撮合 / 碳币充值 / 签发准入证书 / 签发审核员资格证 / 用户管理」全部判给**第三方监管**，而这些在 §3.1 角色表与 docs/raw 里都属于**管理员**。

且表7 中「监管数据查询」一行**全部为「—」**——把该角色唯一的本职功能留空。

### 冲突 C-5：技术架构与使用说明书 对 CarbonController 归属描述错误

原文：「CarbonController | /api/v1/carbon | 碳报告草稿、核算计算、签名提交、上链 | **ENTERPRISE 角色**」
实际 CarbonController 覆盖 ENTERPRISE / REVIEWER / ADMIN 三种角色（/certify = ADMIN、/review = REVIEWER）。**标注为单一 ENTERPRISE 角色是错的。**

## 六、④ 原始需求（L1）内部的多重表述——问题源头

这是本次审计**最重要的发现**，也是此前几轮都没挖到的：

| L1 位置 | 表述 | 指向 |
|---|---|---|
| 数据审核模块 | 「利用数字签名验证结果的有效性，最终提供碳排放报告后上链存储」 | REVIEWER |
| 数据审核模块 | 「验证通过后，数据审核员……将企业碳报告进行铸造和上链」 | REVIEWER |
| 数据审核模块 | 「当数据审核员点击提交碳排放报告后，系统后台**自动**将该报告进行上链」 | 系统自动 |
| 区块链交易流程 | 「提交对等节点即**管理员**在确认无误后将交易区块上链」 | ADMIN |
| 多方审核核算 | 「管理员作为提交对等节点，可在信息**上链前再次审查**碳核算数据」 | ADMIN |

**L1 自己就没说清「上链」到底是审核员触发、管理员触发、还是系统自动。** 下游文档各取所需，分裂由此而来。

**这解释了为什么此前几轮结论会反复**：只取单句就会得出单一口径，取多句才发现源头不一致。

### Q1（最关键）上链触发方式，最终定哪一种？
