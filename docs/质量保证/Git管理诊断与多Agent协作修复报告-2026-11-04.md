## 零、这一轮和上两轮的区别

前两轮做的是「**建护栏**」：补钩子、补租约、补门禁、补分支保护。
结果护栏全部就位，**同一种事故又发生了一次**。

| 轮次 | 关注点 | 结论 |
|---|---|---|
| 第一轮 | 流水线飘红、并发机制从无到有 | 建了 commit-msg / pre-push / lease.mjs |
| 第二轮 | main 变红的真实根因、分支保护真正生效 | CI 转绿、ruleset 落地 |
| **第三轮** | **护栏为什么没起作用** | **护栏是「可选的」，没人调用等于不存在** |

这一轮的结论很直接：**问题不在护栏设计，在护栏的触发时机**。

### 1.2 双方各自实现了同一批需求

`git merge-tree --write-tree` 试合并：**8 个冲突文件，其中 3 个 add/add**。

| 冲突文件 | 类型 | 本质 |
|---|---|---|
| `CarbonService.java` | content ×3 | 配额语义：本地「发碳币」vs 远端「发配额」 |

`add/add` 是最贵的冲突形态：Git 没有共同祖先可参考，只能人肉判断哪一版才是对的。

### 1.3 三道旧护栏为什么全部漏过

| 护栏 | 触发时机 | 本次为何失效 |
|---|---|---|
| `commit-msg` | 新建提交 | 只校验 Conventional Commits **格式**，与内容是否分叉无关 |
| `pre-push` 护栏 1 | 推送时 | 拦「直推 main」——但本地 main **从未推送过**，钩子永不执行 |
| `pre-push` 护栏 2 | 推送时 | Flyway 水位线——同理，不在推送就不会触发 |
| `lease.mjs` | 需人工调用 | `grep -rn "lease.mjs"` 全仓结果：**只有文档提到它，零个调用方** |

**共同点：全部依赖「推送」这个动作，或依赖人主动想起来。**
而本次事故的形态恰恰是「长期不推送」。

## 二、修复清单

### 2.1 收口分叉：按「代码真实状态」裁决，不按「哪边新」

裁决依据不是时间戳，而是**哪一边的代码与运行时不变量一致**：

```java
// 本地 main 的 CarbonService 已注入 CarbonCoinService（第 73 行）
private final CarbonCoinService carbonCoinService;

// 审核通过走 issueCoinQuietly → carbonCoinService.issueForReport
// 驳回回收走 clawbackForReport（不是 revokeForReport）
```

对照 2026-11-03 已落地的业务模型：

```
配额 = 产量 × 基准值   ← 只计算，不发给企业
盈余 = 配额 − 实排
盈余 > 0 → 发 N 枚碳币（1:1）
```

远端 `origin/main` 的版本仍是旧模型（配额直接进 `carbonTradable`）。
**若采信远端，等于把 11-03 的一整轮语义改造回退了**，且不会有任何测试报错——
因为远端自己的那版测试断言的正是旧语义。

具体处置：

| 文件 | 处置 |
|---|---|
| `CarbonService.java` | 全取本地（碳币语义 + 显式置 `REVOKED` 防回写） |
| `QuotaAllocationService.java` | 本地语义 + 采远端补的 `seq` 日志参数（两边都对，合并） |
| `AdminController(Admission)Test.java` | 保留本地 `@MockBean`（远端是纯删除块；缺该 bean 时 `@WebMvcTest` 整类起不来） |
| 3 个 add/add 测试类 | 取本地侧（差异仅在构造器多传 `CarbonCoinService`，与实际字段集一致） |
| `DEV-GUIDE.md` | 取**合并后的实测值**，不采任一单边 |

`DEV-GUIDE.md` 这一处值得单独说：两边写的数字**都是错的**。
本地写「V1-V30 / 2272 词条 / API 模块 23」，远端写「V1-V27 / 2322 / 24」。
合并后实测是 V1-V30、2272、23。我当时先采了远端的「24」，`doc-verify` 立刻报红：

```
✗ 前端 API 模块: 实际=23 文档期望=24
```

这说明门禁在这一处是有效的——**它逼我把数字改回实测值，而不是让我蒙混过去**。

### 2.2 修一处真实的门禁红

`workflow-verify` 在 PR #4 之前是红的：7 个 `.sh` 入库权限为 `100644`。

```
✗ 7 个 .sh 脚本入库权限为 100644（缺可执行位）
    Linux Runner 上 ./xxx.sh 会直接 exit 126 (Permission denied)，
    而 Windows 本地不受影响——缺陷只在 CI 暴露。
```

这 7 个目前未被 workflow 直接调用，但 `scripts/ops/` 是 Fabric/发布运维入口，
一旦接线就是静默失败。已 `git update-index --chmod=+x` 修复，门禁转绿。

> 附带教训：我第一次跑门禁时看到 `EXIT=0` 就以为全绿，实际是
> `node ... | tail -8` 让 `$?` 取到了 `tail` 的退出码。
> **判断门禁结果必须看进程本身，不能看管道末端。**

### 2.3 把并发防护从「人工自觉」改成自动执行

#### 新增 `scripts/agent/preflight.mjs`（只读）

开工前回答三个必须在动手前知道的问题：

| 检查 | 阻断码 | 判据 |
|---|---|---|
| 工作区卫生 | `ON_MAIN` | 当前在 main/master 上 |
| 分叉深度 | `BEHIND_ORIGIN` / `DIVERGED` | 落后远端 / 双向分叉且试合并有冲突 |
| 冲突面 | `OVERLAPPING_FILES` | 同一文件被本地与远端各自独立修改 |
| 租约 | `ACTIVE_LEASES`（仅警告） | 其他任务占着路径 |

设计取舍：

- **只读**。不 fetch、不改 git 状态、不写租约。预检若有副作用，人会怕改变状态而不敢跑。
- **分级退出**。`BLOCK` 非零退出，`WARN` 只提示。全阻塞会让人一律 `--no-verify`。
- **冲突预判用 `git merge-tree --write-tree`**：在临时区试合并、不碰工作区，比凭经验猜准确。

在本次事故现场跑出来的正是它该抓到的东西：

```
✗ [BEHIND_ORIGIN] 本地落后 origin/main 1 个提交。
✗ [OVERLAPPING_FILES] 35 个文件在本地与远端被「各自独立修改」，其中 6 个属于高危区。
❌ 预检未通过：2 个阻塞项，1 个提示项。
```

#### `.githooks/pre-push` 新增护栏 4：推送前复查基线漂移

默认**只警告**，`REQUIRE_UP_TO_DATE=1` 才硬拦。

为什么默认不拦：发布频率低的仓库里，硬拦会让人习惯性 `--no-verify`，
那比不拦更糟。而 CI 与发布流程（`release.mjs`）用严格模式，那里才是必须过的关口。

#### `lint.yml` 新增 Concurrency Guard Self-Test

```
- name: Concurrency Guard Self-Test
  run: node scripts/agent/concurrency-sim.mjs
```

护栏自己失修（比如调用链断了）时 CI 立刻红。这一条是本次最重要的结构性改动：
**把「护栏的护栏」也放进 CI**。

### 2.4 反向验证脚本 `concurrency-sim.mjs`

在 `os.tmpdir()` 的临时沙盒里跑 4 个真实场景，不污染主工作区：

| 场景 | 验证的事 | 期望 | 实测 |
|---|---|---|---|
| S1 | 两个 Agent 改不相交文件 | 合并零冲突 | ✓ rebase/merge 均成功，0 冲突 |
| S2 | 两个 Agent 改同一 i18n 文件 | **确实冲突** | ✓ 产生冲突 |
| S3 | 两侧各自 +1 到同一迁移版本号 | `pre-push` 拦 | ✓ 被 Flyway 水位线拦截 |
| S4 | 在落后远端的基线上开工 | `preflight` 阻断 | ✓ `BEHIND_ORIGIN` |

**S2 的期望结果是「冲突」，这点容易误读**：策略是**禁止同改**（高危路径独占租约），
不是**解决同改**。S2 证明冲突真实存在，从而证明那条禁令不是形式主义。

### 2.5 PR #4 让 26 个提交首次跑 CI —— 抓出三个真实缺陷

这 26 个提交在本地产出、从未推送，因此 CI 从未见过它们。
PR 一开，三道此前「永远绿」的检查立刻变红，每一项都是真实问题：

| # | 失败项 | 真实根因 | 编号 |
|---|---|---|---|
| 1 | Java (PMD + SpotBugs) | 新增代码引入 PMD +16 / SpotBugs +2 | §2.6 |
| 2 | e2e | **后端在 CI 里根本没启动**——fail-closed 校验缺 profile | §2.7 |
| 3 | e2e | 前端模块已删、e2e 断言未同步 | §2.8 |

这正是「护栏必须自动执行」的最强证据：**同样的代码，本地全绿，CI 连挂三次**。

### 2.6 静态分析增量（PMD 434→407，SpotBugs 143→136）

棘轮语义是「只准下降」，所以必须逐条修掉新增项，或加精确抑制。

PMD 净 16 条的构成与处置：

| 条目 | 数量 | 处置 |
|---|---|---|
| `GuardLogStatement` | +9 | 新增日志参数含 `toPlainString()`/`getMessage()`，按仓库既有写法补 `log.isXxxEnabled()` 守卫 |
| `UnusedLocalVariable` | +4 | `TradeAuditService.approve` 中 `amount`/`sellerEnterpriseId`/`buyerEnterpriseId` 是「碳币转让」改造后的死变量 |
| `UnusedFormalParameter` | +2 | `doIssue(operatorId)` 补进日志（保留审计追溯）；`validateFabricProfileAlignment(isProduction)` 在该方法改为「无论环境都拒绝」后确实无用 → 删参 |
| `PreserveStackTrace` | +1 | 证书编号冲突处补 `cause`，否则日志只剩「编号冲突」，看不出是唯一键还是非空约束违规 |
| `UnnecessaryImport` / `FullyQualifiedName` | +2 | 删未用导入、去冗余全限定名 |

SpotBugs 新增 2 条 `DLS_DEAD_LOCAL_STORE`：两处「取 enterprise 只为校验存在性」，
改为不赋值。

**一处踩坑值得单独记**：我一开始把 `TradeAuditService.quotaLedgerService` 也当孤儿依赖删了，
CI 立刻报 `TradeAuditServiceTest:72 constructor cannot be applied`。
那个字段在生产路径确实不再调用，但测试里有 **9 处 `verify(quotaLedgerService, never())`**——
它们是「配额退出资产层」这一模型变更的**可执行证据**。删依赖会让这些断言变成编译错误，
等于把「没有回退到配额账本」的守护一起删掉。最终保留注入 + 一行 `spotbugs-exclude.xml`
精确排除（只匹配这一个字段，不放大到整类）。

**降一条静态告警的代价，不能是删掉一组守护断言。**

### 2.7 e2e 后端启动失败（fail-closed 与 CI 环境的缺口）

日志：

```
java.lang.SecurityException: FATAL: 未激活 'fabric' profile，
区块链将退化为 MockBlockchainService（伪造 tx_mock_ 哈希）。
    at SecurityStartupValidator.validateFabricProfileAlignment(SecurityStartupValidator.java:273)
```

`f726009` 引入了区块链 fail-closed 校验：未激活 `fabric` profile 就拒绝启动，
除非显式 `OAISS_ALLOW_MOCK_CHAIN=true`。而 e2e workflow 里只有
`SPRING_PROFILES_ACTIVE: docker`——没有 fabric、也没有逃生门，于是后端起不来，
整套 e2e 变成「连不上 8080」。

处置：`e2e-tests.yml` 与 `e2e-full-matrix.yml` 补 `OAISS_ALLOW_MOCK_CHAIN: "true"`。

语义边界写进了 workflow 注释，避免后人误解为「放水」：

> 这是「允许启动」而非「允许伪造存证」——该模式下 `MockBlockchainService`
> 不产出任何 txHash，报告停在「审核通过」。e2e 不应断言 `tx_mock_` 假哈希。

没有改 fail-closed 本身——生产/发布仍需真实 Fabric，那一层校验是对的。

### 2.8 e2e 断言与已删模块的漂移

后端起来后，只有 4 例失败，全在 `frontend-coverage-flow.spec.ts`：
断言 `src/api/enterpriseInference.ts` 存在。

根因同样在 `f726009`：它有意删除前端「企业推理」模块
（页面/API/测试/e2e 共 6 文件），commit message 明确写「后端
`EnterpriseInferenceController` 保留」，但漏改了这个 spec 的两处清单。

处置：`requiredFiles` 去掉该文件、去掉对应的 `extractEndpointsFromApiModule` 断言。

**这里我差点改错**：同文件第 86 行的「enterprise inference API endpoint exists」
我一开始也一并改了。但那个用例走 `verifyApiModuleCoverage`，它是按**端点表**
发 HTTP 请求验路由存活，**不读前端文件**——后端端点保留，所以它本来就该通过。
读了 `api-coverage.ts` 的实现后回退了这个改动。

**「看起来相关的两个断言」未必共享同一个失败原因**，改之前要看它实际怎么执行。

### 2.9 过程中修掉的自身缺陷

写这个脚本时踩了三个坑，都值得记下来——它们正是「验证必须真跑」的理由：

1. **`execFileSync` 不接受 `input` 选项**。要给 `pre-push` 喂 stdin 必须用 `spawnSync`。
2. **两者失败语义不同**：`execFileSync` 抛异常，`spawnSync` 只把非零码放在 `.status`。
   不区分的话，**钩子拒绝推送会被误判为通过**——S3 第一版就是这么假绿的。
3. **沙盒 bare 仓库没设 `symbolic-ref HEAD`**，`git clone` 出来是空工作树，
   后续写入因目录不存在而失败。而失败又被 `g()` 吞掉，表现为「合并没冲突」——
   S2 第一版假红就是这么来的。

第 2、3 条共同说明一件事：**一个把失败当成功的测试工具，比没有测试更危险**，
因为它会给出确定性的错误结论。

## 五、给多 Agent 会话的操作卡（第三轮修订）

```bash
# 0. 开工前：先问「这个目录还有谁在用」，而不是「我在哪个分支」
node scripts/agent/preflight.mjs
#   ON_MAIN            → 停手，建 worktree
#   BEHIND_ORIGIN      → git fetch origin && rebase 到最新
#   OVERLAPPING_FILES  → 停手，先合并并跑通测试

# 1. 一个任务 = 一个 worktree = 一个分支
git fetch origin
git worktree add ../t-<id> -b <type>/<scope>-<slug> origin/main
cd ../t-<id>

# 2. 声明路径（高危区必须独占）
node scripts/agent/lease.mjs acquire \
  --task "<type>/<scope>-<slug>" \
  --paths "oaiss-chain-backend/src/main/resources/db/migration/"

# 3. 改完在这个 worktree 里跑门禁——不要在主工作区跑
node scripts/gates/doc-verify.mjs
node scripts/gates/workflow-verify.mjs
node scripts/gates/static-analysis-ratchet.mjs
npm run type-check --prefix oaiss-chain-frontend

# 4. 交付（PR 上 8 项必需检查，绕不过去）
git push -u origin <branch>
```

### 本轮新增的硬规矩

1. **判断门禁结果看进程退出码，不看管道末端**。
   `node gate.mjs | tail` 的 `$?` 是 `tail` 的，会给出假绿。
2. **合并冲突按「代码真实状态」裁决，不按「哪边提交更新」**。
   时间戳只能说明先后，说明不了哪边符合当前运行时不变量。
3. **任何声称「已验证」的工具，必须自己先被负向测试过**。
   一个把失败当成功的测试工具，比没有测试更危险。
4. **护栏的护栏要在 CI 里**。`concurrency-sim` 进 CI，是为了让护栏失修立刻暴露。
