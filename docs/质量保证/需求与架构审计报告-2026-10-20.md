## 二、原始需求提取（L1 证据）

以下为原文摘录（`docs/raw` 第 5.2 / 6.x 节）：

### 2.1 流程环节

| # | 环节 | 原文摘录 | 执行角色 |
|---|---|---|---|
| F1 | 企业填报与签名 | 「该系统将用户核算结果及相应材料发送至数据审核员终端进行人工审核，同时基于安全技术确保数据未经篡改」 | ENTERPRISE |
| F2 | 审核员人工审核 | 同上句；「经数据审核员审核」 | REVIEWER |
| F3 | 审核通过后上链 | 「数据审核模块：……利用数字签名验证结果的有效性，**最终提供碳排放报告后上链存储**」 | REVIEWER（承接 F2） |
| F4 | 碳交易（拍卖→P2P） | 「碳交易分为双向拍卖和P2P交易两个阶段，在系统智能撮合失败后由双向拍卖阶段转向P2P交易阶段，**最后结果上链存储**」 | ENTERPRISE |
| F5 | 管理调控 | 「管理调控模块：该模块实现了信誉分机制和系统配置功能，**管理员**可利用该功能实现对系统和用户的调控和管理」 | ADMIN |
| F6 | 市场信息查询与监管 | 「提供市场信息查询功能……**企业用户仅能检索到匿名交易记录，而管理员用户可查询匿名地址对应的现实用户和市场整体的统计信息**」 | 全角色（按权限） |
| F7 | 下市处罚 | 「**管理员及第三方监管机构**拥有更高权限，可对谎报、瞒报的企业进行'下市'操作」 | ADMIN + THIRD_PARTY |

### 2.2 角色职责（原文）

| 角色 | 原文职责 | 是否含「上链审批」 |
|---|---|---|
| ENTERPRISE | 填报核算、签名、发起交易 | 否 |
| REVIEWER（数据审核员） | 「只需根据后台显示结果进行企业碳核算结果审核」；F3 中「上链存储」紧接审核动作 | **是（执行上链）** |
| THIRD_PARTY（第三方监管） | 「更好地进行用户数据审核及删除用户等操作」；F7 中与管理员同为「下市」执行者 | **否** |
| ADMIN | 「帮助管理员进行系统用户管理及系统配置」；F5 管理调控 | 未提及上链 |

> **结论**：原始需求中，「核准上链」是**审核员审核通过后的紧接动作**，不存在独立的第三方监管审批环节。第三方监管的职责是**监督、查询、下市处罚**，不是流程内审批节点。

## 三、三方对齐走查（L1 ↔ L2 ↔ 实现）

### 3.1 核心冲突：上链职责归属

| 差异项 | L1 原文 | L2 原文 | 实现 | 结论 |
|---|---|---|---|---|
| 上链执行者 | 「最终提供碳排放报告后上链存储」（紧接审核员动作，未提监管） | §4.3「验证通过后，**数据审核员**为该企业提供碳排放报告，并将企业碳报告进行**铸造和上链**」 | `CarbonController.java:238` `@PreAuthorize("hasRole('ADMIN')")` 于 `POST /carbon/certify`；`/certify/batch:258` 同 | **实现偏离 L1/L2**：L1+L2 一致指向 REVIEWER，实现是 ADMIN |
| 监管是否审批上链 | **未找到依据**（无任何原文要求监管核准） | §3.1 角色表：「监管碳报告和交易数据，查看统计信息，**定期核查**」；§4.14「提供监管视角的碳报告**查询**、监管统计和机构信息管理」 | THIRD_PARTY 无任何上链端点；`README` 已改为「宏观监管」 | **监管不审批 = 符合 L1/L2**；`技术架构说明书`「最终上链存证确认」**违反 L1/L2** |

**判定**：
- 「监管核准上链」是 **L4 文档擅自引入的伪环节**，L1/L2 均无依据。
- 真正的偏离是：**实现把上链权交给了 ADMIN，而 L1/L2 写明是 REVIEWER**。
- 因此此前「决策 B」（以实现为准、监管不审批）**方向部分正确**（监管确实不审批），但**它同时默认了 ADMIN 代行也是对的，这一点与 L1/L2 冲突，未被发现**。

## 四、差异清单与设计决策

### D-01 上链核准归属：ADMIN vs REVIEWER

| 项 | 内容 |
|---|---|
| **原文依据** | L1：「最终提供碳排放报告后上链存储」（紧接审核员审核）；L2 §4.3：「验证通过后，**数据审核员**……将企业碳报告进行**铸造和上链**」 |
| **实现位置** | `CarbonController.java:238`（`/certify`）、`:258`（`/certify/batch`），均为 `hasRole('ADMIN')` |
| **差异** | 实现把 L1/L2 明确的 REVIEWER 职责移交给了 ADMIN |
| **设计决策** | **改为 REVIEWER**（向 L1/L2 收敛）。理由：L1 与 L2 §4.3 两处独立表述一致，不属孤证 |
| **影响面** | 后端 2 个注解；前端菜单 `/admin/verify/list` 需迁至审核员端；`VerifyList.vue` 归属调整；`证据索引`/`README` 角色描述回改 |
| **改动代价** | 后端约 10 分钟；前端菜单+路由约 1 小时；文档同步约 30 分钟 |
| **风险** | 审核员同时「判断合规」和「执行上链」，失去双人复核。但**这正是原始需求的设计**——L1 未设第二道审批。若需制衡，应作为**新增需求**提出，不能伪装成既有需求 |

### D-02 第三方监管是否应有上链审批权
