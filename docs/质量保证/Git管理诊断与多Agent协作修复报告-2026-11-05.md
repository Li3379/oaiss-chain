## 一、诊断：这次到底哪里坏了

### 1.1 表面现象与真实根因

| 观察到的现象 | 第一直觉 | 实际根因 |
|---|---|---|
| `main` 领先 origin 13 个提交 | 「忘了推送」 | **推送被护栏自己拦住了** |
| 九项门禁本地全绿、并发自检 4/4 通过 | 「机制健康」 | 自检场景**没有覆盖小数版本**这条路径 |
| 分支保护 8 项必需检查齐备 | 「CI 已完备」 | CI 完备，但**提交能绕过 CI 在本地堆积** |
| 三个历史分支看起来都有未合并内容 | 「不能删」 | squash 合并导致 `git cherry` 误判，需按**内容**验证 |

### 1.2 缺陷 1（P0）：`pre-push` 封锁全部推送

**现象**：构造一条推送到非 main 分支的 ref 行，钩子直接 `exit 1`。

**根因**：`version_of()` 的正则只认整数段：

```bash
# 修复前
basename "$1" | sed -nE 's/^V([0-9]+)__.*/\1/p'
```

`V29_1__...sql` 不匹配 → 返回空 → 被 `[ -z "$v" ]` 判成「命名不合规」。

**为什么 V29_1 是合法的**：Flyway 版本号允许分段（`29.1`），文件名写成 `V29_1__`。
本项目用它给 V30 的唯一索引做**数据前置修复**（先去重历史 cert_no，再建唯一索引），
并且 `application.yml` 已显式开启 `flyway.out-of-order: true` 来支持这种补跑。

**修复的三层**：

1. **识别小数段**
   ```bash
   raw="$(basename "$1" | sed -nE 's/^V([0-9]+(_[0-9]+)*)__.*/\1/p')"
   printf '%s' "${raw//_/.}"     # V29_1 -> 29.1
   ```

2. **改用数值键比较**（这一层最隐蔽）

   原实现直接比字符串：
   ```bash
   [ "$v" -le "$watermark" ]   # "29.1" -le 30
   ```
   字符串语义下 `"29.1" > "30"`（第 2 字符 `9` vs `0`），而 Flyway 是逐段**数值**比较
   （`29.1 < 30`）。口径反了，水位线判断就会反向——**放行真撞车、拦截合法迁移**。

   ```bash
   ver_key() {
     local v="$1" major minor patch
     IFS='.' read -r major minor patch <<<"$v"
     printf '%d' "$(( ${major:-0} * 100000000 + ${minor:-0} * 10000 + ${patch:-0} ))"
   }
   ```

3. **尊重运行期策略**（这一层是设计问题，不只是代码问题）

   护栏一律硬拦「版本号 ≤ 水位线」，但项目已经开启 `out-of-order`。
   于是出现「CI 全绿、本地推不出去」的自相矛盾状态。

   现改为读配置决定行为：

   | `flyway.out-of-order` | 低版本迁移的处理 |
   |---|---|
   | `false`（默认） | 硬拦（已部署环境会拒绝启动） |
   | `true`（本项目） | 降级为提示，并告诫只放幂等数据修复 |

**验证**：

| 项 | 结果 |
|---|---|
| `V29__` → 29 / `V29_1__` → 29.1 / `V30__` → 30 / 非法名 → 空 | ✅ |
| `29.1 < 30`、`29.2 > 29.1` | ✅ 与 Flyway 语义一致 |
| 真实 `main` 推送现在通过 | ✅ `exit 0` |
| S3（两侧各自 +1 到 V31）仍被拦 | ✅ 真撞车没被放过 |
| 直推 main 仍被拦 | ✅ `exit 1` |

### 1.3 缺陷 2（P0）：没有任何机制拦截「在 main 上提交」

这是本轮最重要的结构性发现。

**两次事故的同一形态**：

```
2026-11-04  本地 main 积压 26 个提交，从未推送
2026-11-05  本地 main 积压 13 个提交，从未推送
```

**为什么 `pre-push` 拦不住**：它的检查时机是**推送时**。而提交可以无限积压、
永不推送——护栏在这条路径上等于不存在。这是**时机错配**，不是护栏太弱。

**更隐蔽的后果**：本地 main 一旦领先 `origin/main`，这些提交就再也不会被 CI 看见
（分支保护只在 PR 上跑检查）。人跑了九项门禁就以为「验过了」，而 8 项必需检查
（含后端 174 个测试类、e2e）一次都没执行。

**修复**：新增 `.githooks/pre-commit`，把拦截点前移到**产生提交的那一刻**。

```
git commit（在 main 上）  -> exit 1，打印可直接照抄的 worktree 命令
ALLOW_COMMIT_MAIN=1       -> exit 0（合并/revert/热修，打印留痕提醒）
detached HEAD             -> exit 0（rebase 中间态需要能落提交）
功能分支                   -> exit 0
```

**验证**：四种场景 + 一次**真实 `git commit`** 全部符合预期（不是只测钩子脚本本身）。

### 1.4 缺陷 3（P1）：`commit-msg` 惩罚了它本该鼓励的写法

并发模拟中合并两个 branch 时暴露：

| 提交信息 | 修复前 | 说明 |
|---|---|---|
| `Merge branch 'x'` | PASS | git 默认写法 |
| `merge: 合入独立改动` | **REJECT** | 符合 Conventional Commits |

Conventional Commits 确实没有 `merge` 这个 type，所以严格说 `merge:` 不是规范写法。
但结果是**回到 git 默认的 `Merge branch ...` 才能过**——护栏逼人退回到更不可读的写法，
方向错了。现同时放行 `merge:` / `revert:`。

**回归 8 例**：`Merge branch 'x'` / `merge:` / `Revert "x"` / `revert:` / `feat(auth):`
全部 PASS；`update` / `修复bug` / `WIP` 仍 REJECT（脏信息没被放过）。

### 1.5 缺陷 4（P1）：依赖与安全更新完全停摆

实测仓库安全配置：

```json
{ "dependabot_security_updates": "disabled",
  "secret_scanning": "enabled",
  "secret_scanning_push_protection": "enabled" }
```

密钥扫描开了，但 **CVE 不会自动开 PR**，依赖升级没有节奏。本仓历史上就攒过一批
再清（axios / echarts / vite / postcss / nanoid / ws 一轮全升），这类「攒一批」的
做法风险最高：小版本累积成大跳，回归面一次性展开。

**修复**：新增 `.github/dependabot.yml`，覆盖 5 个生态
（maven / npm-frontend / npm-scripts / pip / gomod / github-actions），统一每周一，
patch+minor 分组、**major 不分组**（破坏性变更必须单独审视）。

按生态锁定了不能由机器人单方面推进的大版本：

| 依赖 | 锁定原因 |
|---|---|
| Spring Boot parent major | Java 17 是运行时基线，升级需同步改三处构建配置并全回归 |
| Playwright major | 大版本改变选择器/断言行为，且 e2e 已为当前版本固定 ubuntu-24.04 |

并通过 API **启用**了 `dependabot_security_updates`（`disabled` → `enabled`）。
启用后立即产生 5 个 PR，确认配置生效。

> 其中 #10 与 #11 是同一批 `vue-i18n` 升级被拆成两个 PR（分组按包切分所致），
> 已关闭重复者并说明原因。

## 二、多 Agent 并发：实机验证（不是读文档）

前几轮的验证是 `concurrency-sim.mjs` 的沙盒场景。本轮补了**真实工作区**的并行验证。

### 2.1 场景：两个 Agent 同时改不相交文件

```bash
git worktree add ../oaiss-sim-a -b sim/agent-a origin/main
git worktree add ../oaiss-sim-b -b sim/agent-b origin/main
# A 改 docs/sim/a.md，B 改 docs/sim/b.md，各自独立提交
git merge sim/agent-b
```

**结果**：`conflicts = 空`，合并后 `a.md` 与 `b.md` 都在。**零冲突、零冗余。**

> 顺带发现：worktree 里检出的 `.githooks` 是 `origin/main` 的旧版本，
> 不含本轮修复。这其实**正向证明**了 worktree 隔离有效——每个工作区用自己基线的钩子。

### 2.2 场景：路径租约硬冲突

```bash
# Agent A 认领 i18n 目录
node scripts/agent/lease.mjs acquire --task "sim/agent-a" --paths ".../i18n/locales/"

# Agent B 认领同一目录
node scripts/agent/lease.mjs acquire --task "sim/agent-b" --paths ".../i18n/locales/"
```

**结果**：

| 情形 | 退出码 | 行为 |
|---|---|---|
| 同路径前缀 | **1** | 硬冲突，列出占用方任务名/主机/到期时间，给出 3 种处置方式 |
| 不相交路径 | 0 | 放行 |

### 2.3 场景：`preflight` 汇总并发信号

同时存在「其他 worktree + 活跃租约 + 脏工作区」时，`preflight` 一次性报出全部四项：

```
⚠ [DIRTY_WORKTREE]       工作区有 1 个已跟踪文件被修改（未提交）
⚠ [OTHER_WORKTREES]      存在 2 个其他 worktree
⚠ [UNVERIFIED_COMMITS]   本地领先 origin/main 18 个提交，从未经过 CI
⚠ [ACTIVE_LEASES]        存在其他任务的活跃租约
✓ 无阻塞项（4 个提示项）
```

注意最后一行：这些是**提示**不是**阻塞**。设计取舍是「全阻塞会让人一律 `--no-verify`」。

### 2.4 清理

模拟产物全部回收：2 个 worktree、2 个分支、2 个租约。`git worktree list` 恢复到
仅主工作区，`lease status` 显示「（无）」。

## 四、版本化：现状与落地路径

### 4.1 现状（未完成的部分）

```
tag 数：0
Release 数：0
CHANGELOG 最新：1.7.1
版本三方对齐：pom 1.7.1 / backend pom 1.7.1 / frontend 1.7.1  ✅
```

**脚本可用，但流程从未真实走过一次。** `release.mjs` 有 7 项前置检查
（版本递增 / CHANGELOG 非占位 / 版本门禁 / 在 main / 工作区干净 / 不落后远端 /
当前提交 CI 全绿 / tag 未占用），并且**默认干跑**。

实测干跑正确拦截了当前状态（缺 CHANGELOG 段落、不在 main 上），说明检查有效。

### 4.2 为什么本轮没有直接打 tag

发布流程的前置条件是「CHANGELOG 有对应段落 + main 全绿」。本轮所有改动都属于
**工程治理**（钩子、CI 配置、协作契约），没有业务功能变化——它们本身不该撑起
一个版本号。硬凑一个 1.7.2 只会污染版本语义：版本号要回答「系统能力有什么变化」，
而不是「今天修了几个护栏」。

所以本轮只把流程写成可照抄步骤（见协作契约 §5.1），等下一个**有业务变更**的版本
再走完整发布。这也符合 `release.mjs` 的设计意图——它拒绝空壳 CHANGELOG 段落，
正是为了防止「为了打 tag 而写一段凑数的话」。

### 4.3 发布流水（已写入 `docs/开发手册/多Agent协作-Git契约.md` §5.1）

```
写 CHANGELOG → 对齐三处版本号 → 提交版本变更
  → release.mjs 干跑 → release.mjs --tag --push → gh release create
```

**顺序不能反**：先打 tag 再补文档 = 发布了一个「没人知道改了什么」的版本。
`release.mjs` 会拒绝少于 30 字的空壳段落。

Tag 是**全局命名空间**，没有路径可租。两个会话同时发布同一版本，后者会在
`--push` 被远端拒绝（non-fast-forward），不会静默覆盖。更早的信号是干跑时的
「tag 未占用」检查。

## 五、加固：CODEOWNERS 与安全配置

### 5.1 CODEOWNERS

本仓冲突的形态不是「抢同一个函数」，而是**结构性重叠**：

| 路径 | 冲突机制 |
|---|---|
| `db/migration/` | 版本号必须全局唯一递增，撞车后已部署环境拒启动 |
| `i18n/locales/` | 巨型对象，任何两人同改必冲突 |
| `DEV-GUIDE.md` | 架构事实数字是全仓汇总 |
| `.github/workflows/` | 改错一次，整条门禁假绿 |

已显式声明 owner。

**诚实说明**：ruleset 当前 `require_code_owner_review = false`，所以这份文件
目前是**声明与可追溯**用途（GitHub 自动加 reviewer），**不是强制门禁**。

### 5.2 为什么没有开启强制审查

仓库只有 1 个人类贡献者（`Li3379` / `god-alis`）。GitHub 不允许 PR 作者批准自己的
PR，因此 `required_approving_review_count ≥ 1` 或 `require_code_owner_review = true`
会**永久阻塞所有合并**——包括紧急热修。

这是单人仓库的固有限制，不是配置疏漏。若将来加入第二人，应在 ruleset 打开：

```
pull_request.require_code_owner_review = true
pull_request.required_approving_review_count = 1
```

### 5.3 已生效的仓库设置变更

| 设置 | 变更 | 理由 |
|---|---|---|
| `dependabot_security_updates` | disabled → **enabled** | CVE 自动开 PR |
| `delete_branch_on_merge` | false → **true** | 合并后自动清理，减少冗余分支 |
| `allow_update_branch` | false → **true** | PR 落后时可一键更新 |
| `sha_pinning_required` | 尝试 true → **回退 false** | 现有工作流全用 `@v4` 标签引用，开启会立即全红 |

> `sha_pinning_required` 的回退是**有意识的取舍**：安全上应开启，但需要先把
> 9 个 action 引用全部固定成 commit SHA。这属于独立任务，不该混在本轮里
> 用一个「让 CI 变红」的开关完成。

### 6.5 反向验证（不是「跑一遍看绿」）

| 验证项 | 方法 | 结果 |

| `pre-commit` 拦 main | 真实 `git commit` | ✅ exit 1 |

| 租约不误伤 | 不相交路径 | ✅ exit 0 |

## 七、给多 Agent 会话的操作卡（第四轮）

```bash
# 0. 开工前：先问「这个目录还有谁在用」
node scripts/agent/preflight.mjs
#   ON_MAIN            -> 已在 pre-commit 层拦截，需先建 worktree
#   BEHIND_ORIGIN      -> git fetch origin && rebase
#   OVERLAPPING_FILES  -> 停手，先合并跑通再开新任务
#   ACTIVE_LEASES      -> 确认路径不重叠

# 1. 一个任务 = 一个 worktree = 一个分支
git fetch origin
git worktree add ../t-<id> -b <type>/<scope>-<slug> origin/main
cd ../t-<id>

# 2. 高危区必须独占（迁移号 / i18n / DEV-GUIDE / workflows）
node scripts/agent/lease.mjs acquire \
  --task "<type>/<scope>-<slug>" \
  --paths "oaiss-chain-backend/src/main/resources/db/migration/"

# 3. 改完在**这个 worktree 里**跑门禁
node scripts/gates/doc-verify.mjs
node scripts/gates/version-verify.mjs
npm run type-check --prefix oaiss-chain-frontend

# 4. 交付：PR 上 8 项必需检查，绕不过去
git push -u origin <branch>
gh pr create --fill
gh pr checks --watch

# 5. 收尾
node scripts/agent/lease.mjs release --task "<type>/<scope>-<slug>"
gh pr merge --squash --delete-branch
git worktree remove ../t-<id>
```

### 本轮新增的硬规矩

1. **不要在 main 上提交**。`pre-commit` 会拦。逃生门 `ALLOW_COMMIT_MAIN=1`
   只用于合并/revert/热修，且会在 log 里留痕。
2. **小数迁移版本是合法的**。`V29_1__` 这种写法允许，护栏已支持；但**只能放
   幂等数据修复**，不能携带新的表结构依赖（它会在高版本之后才执行）。
3. **判断分支能否删，看内容不看名字**。squash 合并会让 `git cherry` 全部误判，
   要逐文件确认 `git cat-file -e main:<path>`。
4. **依赖升级走 Dependabot，不要再攒批**。major 版本单独审视，不与 minor 混提。

## 九、一句话总结

前三轮解决的是「护栏不存在或没人调用」；本轮解决的是「护栏把合法操作拦死了」。

最值得记住的一条：**`pre-push` 拦不住「永不推送的提交」**。
两次各积压 26 / 13 个提交的事故形态相同，根因是**检查时机**而非检查强度——
所以护栏必须前移到「产生提交的那一刻」。

验证方式同样值得记住：本轮每个修复都跑了**负向用例**（还原旧代码看测试是否变红），
否则「修完测试通过」只能证明测试和代码一起改对了，不能证明测试能抓到回归。
