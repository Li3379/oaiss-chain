## 三、A 类：数字事实不符（3 项）

### A-1 · i18n 词条数：宣称 1432，实际 1441（差 9）【中】

- **文档出处**：
  - `DEV-GUIDE.md` §11：`i18n 词条 | 1432 | zh-CN 与 en-US 严格镜像`
  - `docs/文档索引.md` 表 4.1.1：`双语国际化词条 | 1,432 对称`
- **实测值**：**1441**（zh-CN 与 en-US 各 1441，零单侧缺失、零重复）。
- **复核方式**（双重独立验证）：
  1. 执行 `node scripts/i18n-verify.mjs` → 输出 `✓ zh-CN 键: 1441｜en-US 键: 1441`；
  2. 我用与脚本**同构的嵌套键解析算法**独立重算 → 同样得 1441。
- **性质**：镜像一致性**完全正确**（这点没问题），仅**总数**少报 9 个。属「统计未随新增词条同步」。
- **影响**：低。但会让人误判「词条没变过」。
- **建议**：把 §11 与表 4.1.1 改为 1441；并考虑让 doc-verify 也接管 i18n 断言（见 B-1）。

### A-2 · 「数据库物理表 25 张」口径失真：实际现存 24 张【中】

- **文档出处**：
  - `docs/文档索引.md`：`数据库物理表 | 25 | Flyway 迁移脚本中 CREATE TABLE 去重统计 (含退场表)`
  - `DEV-GUIDE.md` §11：`Tables | 25 | 含 1 张退场 authenticator 与 outbox_message`
  - `scripts/gates/doc-verify.mjs`：`tables: 25, // 含 1 张退场 authenticator`
- **实测**：
  - 迁移脚本 `CREATE TABLE` 去重 = **25 张**；
  - 其中 `authenticator` 已在 **V8** 被 `DROP TABLE`；
  - **现存表 = 24 张**；
  - 运行时 MySQL `information_schema` 实查 = **26 张**（= 24 业务表 + `flyway_schema_history` + 1 张系统表）。
- **性质**：**统计口径把「曾创建」当「现存」**。文档用「含退场表」自我解释，但对外表述「物理表 25 张」会被理解为「现在有 25 张」，与事实不符。
- **影响**：中。做容量评估、备份策略、数据字典时会多算一张。
- **建议**：改为双数字表述，例如「现存 24 张（迁移历程中共创建 25 张，`authenticator` 已于 V8 退场）」。

### A-3 · 门禁脚本内部注释与期望值不同步风险【中】

- **现象**：`doc-verify.mjs` 的 `EXPECT` 常量注释写「含 1 张退场 authenticator 与 1 张 outbox_message」，但 `tables: 25` 的算法是 `CREATE TABLE` 去重，**并未扣除被 DROP 的表**。即脚本断言的「25」本身就是一个**脏计数**，它却输出 `✓ 数据表 (CREATE TABLE 去重): 实际=25 期望=25`，给人「已核对」的错觉。
- **性质**：断言通过 ≠ 事实正确。这是**断言设计缺陷**，会掩盖 A-2。
- **建议**：把该断言改为「现存表数」口径（解析 DROP TABLE 并扣除），期望值改 24。

## 四、B 类：文档声明与机制不符（2 项）—— 本报告最重要的发现

### B-1 · `doc-verify.mjs` 是「假门禁」：自称防止文档漂移，却从不读取文档【高】

- **文档声明**：
  - `DEV-GUIDE.md` 开头：「本文件是开发时唯一必读的权威文档……所有事实经断言脚本自动校验，与代码零漂移」
  - `docs/文档索引.md` 表 4.1.1 末注：「以上数字由 `scripts/doc-verify.mjs` 自动断言」
  - 脚本输出原话：**`✅ 全部断言通过 — 文档与代码零漂移`**
- **实测真相**：直接阅读 `scripts/gates/doc-verify.mjs`（135 行）发现：

| 检查维度 | 实际情况 |
|---|---|
| 是否读取任何 `.md` 文档 | **否**（全文无 `readFileSync(...md)`，只在注释里提到 DEV-GUIDE） |
| 期望值来源 | **硬编码在脚本内 `const EXPECT = {...}`**，不是从文档解析 |
| 是否检查 i18n 词条 | **否**（全文无 i18n/1432 字样） |
| 是否检查「数据库物理表」是否正确口径 | 否（只做 CREATE TABLE 去重，见 A-3） |

- **它实际做的事**：`代码实际计数` 与 `脚本内写死的 EXPECT` 比较。
  → 只要有人改代码时顺手改了 `EXPECT`，它就永远 PASS；
  → 而文档正文写的是 1432，脚本根本不看，所以**永远发现不了 A-1**。
- **运行结果**（我实际执行）：
```
✓ Controllers: 实际=23 期望=23
✓ REST 端点: 实际=146 期望=146
✓ Services (主包): 实际=34 期望=34
✓ 数据表 (CREATE TABLE 去重): 实际=25 期望=25 (含退场 authenticator)
✅ 全部断言通过 — 文档与代码零漂移
```
  注意最后一行措辞——**「文档与代码零漂移」，但脚本从没读过文档**。这是名不符实。
- **影响（高）**：
  1. 给人虚假安全感：团队会以为「跑过 doc-verify 就是文档正确」，实际文档可能全错。
  2. 已造成事实后果：A-1（1432 vs 1441）与 A-2（25 vs 24）都因此长期未被发现。
  3. 交接/评审场景风险最大：外部评审若真去核数字，会立刻发现「自称断言通过但数字是错的」。
- **建议（按投入排序）**：
  - **最低成本**：把输出文案改为「代码结构零漂移（未校验文档正文）」，杜绝误导。
  - **推荐**：让脚本真正解析 `DEV-GUIDE.md` §11 的表格取值，与代码比对；这样文档写错会被抓出。
  - **合并**：把 `i18n-verify.mjs` 的 1441 断言并入同一门禁，避免三套脚本口径分裂。

### B-2 · 三个门禁脚本全部未接入 CI，等于「无人自动执行」【高】

- **文档声明**：`DEV-GUIDE.md` §8 开发流程写「改代码后运行: `node scripts/doc-verify.mjs && node scripts/role-matrix-verify.mjs`」；`docs/文档索引.md` 1.2 节写「CI 交付闭环门禁阻断：所有发布流水线通过 `closure-audit.mjs` 强制核验」。
- **实测**：检查 `.github/` 全部文件——

| 文件 | 是否调用门禁脚本 |
|---|---|
| `.github/workflows/deploy-release.yml` | 否 |
| `.github/workflows/e2e-tests.yml` | 否 |
| `.github/workflows/lint.yml` | 否 |
| `.github/workflows/load-tests.yml` | 否 |
| `.github/workflows/release-images.yml` | 否 |

**5 个 workflow 无一调用 `doc-verify` / `i18n-verify` / `role-matrix-verify` / `closure-audit`。**
- **影响的定性**：这不是「脚本不好」，而是**「脚本再好也无人跑」**。文档说「CI 强制阻断」属于**未实现的宣称**。
- **补充事实**：三个脚本本身都能正常执行且当前都 PASS（我逐一跑过，退出码 0）：
  - `doc-verify.mjs` → 12 项断言全 ✓；
  - `i18n-verify.mjs` → 1441/1441、代码引用 1186 键全部存在 ✓；
  - `role-matrix-verify.mjs` → 4 项角色语义 ✓（含「审核通过自动上链」「第三方监管无写端点」）。
  所以问题是**接线缺失**，不是脚本质量问题。
- **建议**：在 `lint.yml` 或新增 `gates.yml` 中加一步：
```yaml
- name: Doc & Role Gates
  run: |
    node scripts/gates/doc-verify.mjs
    node scripts/gates/i18n-verify.mjs
    node scripts/role-matrix-verify.mjs
    node scripts/gates/closure-audit.mjs
```
  并设为 required check，才能真正实现文档所承诺的「阻断」。

## 五、C 类：功能缺陷（已实测可复现，3 项）

### C-1 · 双向拍卖页「共 N 条」计数错误【高】

- **现象**：`/enterprise/trading/market` 页面，表格上方提示文本显示 **「共 0 条」**，但同一页面的分页控件显示 **「共 42 条」**，且表格实际渲染 **10 行**。
- **实测复现**（Playwright 无头浏览器登录 `enterprise001`）：
```
D-01 实测 => table-tip:[共 0 条] pagination:[共 42 条] rows:10
4xx 请求: 无
AI 建议卡片存在: true
```
- **根因**：`oaiss-chain-frontend/src/views/enterprise/TradingMarket.vue:388`
```html
<div v-if="activeTab !== 'match'" class="table-tip">{{ t('common.total', { count: selectedRows.length }) }}</div>
```
  把 **`selectedRows.length`（当前勾选行数，初始为 0）** 当成了**总记录数**渲染，应使用页面数据里的 `total` 变量。
- **影响（高）**：
  1. 用户会误以为市场没有挂单（对「双向拍卖」这种核心展示页是破坏性的）。
  2. 演示时非常扎眼，容易被评审直接指出。
- **建议**：把 `selectedRows.length` 改为 `total`。若该行的本意是「已选 N 条」，则应改用独立文案（如「已选 N 条」）以避免与分页总数语义冲突。

### C-2 · 企业用户无法触发拍卖撮合（产品语义待商榷）【中】

- **现象**：企业在「双向拍卖」大厅只能挂单，无法撮合；`POST /auction/match` 仅 ADMIN 可调。
- **实测**：
  - `enterprise001` 调 `POST /api/v1/auction/match` → **403 / code 2004 / error.permission.denied**；
  - `admin` 调同一接口 → **200 操作成功**。
- **源码**：`DoubleAuctionController.java:96` 上方 `@PreAuthorize("hasRole('ADMIN')")`（第 104 行附近，源码注释「仅管理员可执行撮合」）。
- **定性**：**是刻意的权限设计，不是 bug**。但从产品语义看：
  - 「双向拍卖大厅」由**管理员手动点触发撮合**，在真实交易所场景不常见（通常是定时自动撮合）；
  - 前端页面也未向企业用户说明「撮合由管理员统一发起」，企业会在「看到有挂单但一直不成交」时困惑。
- **建议（三选一）**：
  1. 增加**定时自动撮合**（推荐，符合 CDA 语义）；
  2. 前端在撮合结果页明确提示「撮合由平台定期统一执行」；
  3. 至少在本缺陷提交时，在代码注释/文档中说明该设计意图。

### C-3 · 信用事件历史仍残留英文描述（新数据已正常）【中】

- **现象**：`/enterprise/credit/score` 的「评分历史」部分**历史行**「原因」列仍是英文，如 `Deduction toward WARNING`、`Score recovery test`、`x`、`test`。
- **实测数据**：`credit_event` 表共 223 条，其中 **英文 171 条、中文 52 条**（SQL：`SELECT CASE WHEN LEFT(event_description,1) REGEXP BINARY '^[A-Za-z]' THEN 'EN' ELSE 'ZH' END, COUNT(*) ... GROUP BY 1`）。
- **根因**：本属 D-02/V14 遗留。V14 迁移只本地化了两类**生产代码生成**的文案（认证奖励、审核驳回），**有意跳过**测试/压测造数（迁移脚本注释已明确说明）。`CarbonService.java` 现已改为 `MessageUtils`，所以**新产生的记录必然是中文**（实测最新记录为「碳报告认证通过奖励」「碳报告审核驳回：report_xxx」）。
- **影响（中）**：演示时若翻到历史旧记录，会看到中英混杂，造成「系统没做国际化」的观感。
- **建议**：
  1. 演示前用演示账号产生新记录；
  2. 或清理/标注这些测试数据（`Deduction toward ...`、`x`、`test` 等确属造数）；
  3. 结构性根治：把 `credit_event.event_description` 改为「事件类型枚举 + 参数」，由前端按 i18n key 渲染，一劳永逸。

## 六、D 类：表述与实际用法偏差（5 项，均低）

### D-1 · 「本地默认启用 Mock 区块链」对当前环境不成立【低】

- **文档出处**：
  - `README.md`：「本项目经过深度轻量化调优，**日常开发完全不需要在本地安装笨重的 Hyperledger Fabric 节点网络**（后端默认集成 Mock 区块链引擎，自动模拟生成合法哈希）」；「本地默认使用 `MockBlockchainService`，所有存证与交易哈希在内存毫秒级生成」
  - `docs/OAISS_CHAIN_技术架构与使用说明书.md`：「本地开发默认启用 Mock 区块链引擎」
- **实测真相**：当前实例**真实连了 Fabric**：
```
GET /api/v1/blockchain/status
→ {"connected":true,"mode":"FABRIC","mspId":"Org1MSP","channel":"mychannel",
   "chaincode":"carbon-chaincode","peers":1,"orderers":1}

GET /api/v1/blockchain/blocks/latest
→ block[0]: {n:30, hash:"0x2f52b8c8...", tx:1, type:"REGULAR", ch:"mychannel"}
```
  且 `docker ps` 显示 `peer0.org1.example.com`、`orderer.example.com`、`ca.org1.example.com`、`dev-peer0...carbon-chaincode` 全部在运行。
- **性质**：文档描述的是**默认 profile（!fabric）**，但**当前环境激活了 fabric profile**。文档并非错误，而是**未说明「当前实际跑的是哪种」**，容易让人误判「你看到的数据是假的」。
- **影响（低但尴尬）**：演示时若讲「我们用的是 Mock」，而实际连了真链，等于**自己给自己降级**；反之若讲「真链」而听众按 README 以为是 Mock，也会困惑。
- **建议**：在 README 增加一句「校验当前模式：访问 `/blockchain/status` 看 `mode` 字段（`FABRIC` / `MOCK`）」，并注明本项目实测环境为 FABRIC。

### D-2 · 官网首页性能指标为静态营销数字【低】

- **现象**：首页展示「99.96% 分布式 / A+ 集中式指标 / **3248 节点数量** / **11ms 延迟** / 49ms 最大延时」。
- **实测**：真实 Fabric 网络为 **1 peer + 1 orderer + 1 CA**，节点数不可能是 3248；延迟未测但与「11ms」无关。
- **性质**：营销展示文案，非系统指标。
- **影响（低）**：对外正式汇报若被追问会被识破。
- **建议**：要么接 `/blockchain/status` 与 Prometheus 实时渲染，要么明确标注「目标架构指标 / 演示数据」。

### D-3 · 部分页面内容明显偏薄（产品完成度不均）【低】

- **实测数据**（Playwright 抽取页面可见文本长度）：

| 页面 | 文本量 | 表格行数 | 评价 |
|---|---|---|---|
| `/enterprise/company/dashboard` 数据可视化 | **372 字符** | 0 | 企业最高频页面，却最弱 |
| `/admin/data/statistics` 统计数据 | **140 字符** | 0 | 仅 4 个数字 + 1 张环形图 |
| `/enterprise/emission/data` 排放数据 | 337 字符 | 5 | 表单+表格可用，图表偏少 |
| `/enterprise/info` 企业信息 | 361 字符 | 0 | 两张信息卡，符合预期 |
| 对比：`/enterprise/enterprise-inference` | 1419 字符 | 0 | 内容充实 |

- **影响（低）**：不是功能错误，但「数据可视化」页作为企业日常入口，信息密度明显不足。
- **建议**：补配额消耗趋势、Scope1/2/3 占比、同业对标雷达、月度环比；统计数据页补上链成功率、审核时效、交易额趋势。

### D-4 · 审核员人力单点（数据配置问题，非代码缺陷）【低】

- **实测**：17 个用户中审核员仅 **1** 人（`reviewer001`），却承担待审 6 条 / 累计历史 34 条。
- **性质**：种子数据配置问题，不是代码 bug。
- **影响（低，但生产隐患）**：生产环境若照此配置，审核环节会成瓶颈。
- **建议**：增加审核员种子账号；引入任务分配（轮询/负载优先）；加审核超时提醒。

### D-5 · 管理员与审核员共用「上链补救」同一组件，职责边界重叠【低】

- **现象**：`/auditor/verify/list`（审核员，标题「上链补救」）与 `/admin/verify/list`（管理员，标题「认证列表」）**渲染同一个组件** `views/admin/VerifyList.vue`，按钮文案同为「批量上链补救」。
- **源码**：`router/index.ts:146-153` 明确注释「本页面上链入口从管理员端迁移到审核员端，承担自动上链失败的幂等补救职责」，`meta.roles = [ROLE.REVIEWER, ROLE.ADMIN]`。
- **性质**：**刻意的双入口设计**，不算错误。
- **影响（低）**：权限边界略模糊——同一动作两个角色都能做。
- **建议**：在文档中明确「审核员为一等补救责任人，管理员为兜底」，避免双人重复操作。
